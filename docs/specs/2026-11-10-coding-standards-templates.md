# Spec：编码规范模板收进仓库

> **⚠️ 事后补写。** 本规格写于实现完成之后（2026-11-10），不是事前批准的方案。
> 用途是**审阅与对照**，不是决策。实现已合入 `master`（`ed7122e`）。
> 补写原因：用户原本调用 `@to-spec` 要求先出规格，被跳过直接实现了。见
> [skill 流程被跳过](../wiki/issues/2026-11-10-skill-process-skipped.md)。

## Problem Statement

一个人想给自己项目配一份编码规范，面对空白的 `CODING_STANDARDS.md` 无从下笔：

- 不知道该写什么——写长了没人读，写短了没用
- 不知道什么该进文档、什么该做成检查
- 看到别人家的规范，分不清哪些是通用原则、哪些是某个仓库自己的事故

调研报告（`docs/reports/2026-11-10-coding-standards-research.md`）给出了理论和一手材料，
但那是给人读的分析，不是能拷走用的东西。

## Solution

在仓库根放一个 `CODING_STANDARDS/` 目录，里面有三份可直接拷进项目使用的规范模板：
TypeScript、Python、Java，外加一份索引 README。

每份模板给出**形态**（祈使句标题 + 为什么 + 谁在强制）、一组示例规则、
"不写什么"的排除表、以及"这份文件怎么变长"的维护机制。
索引 README 顶部醒目说明：示例事故是编的，照抄前必须替换。

全局 README 在「装到本地」之后加一节，让找的人不用翻目录树就看得到。

## User Stories

1. 作为一个想给自己项目配编码规范的开发者，我想要一份可直接拷走的模板，这样我不用从空白文件开始。
2. 作为读模板的人，我想要每条事故都标注是示例，这样我不会引用从未发生过的 bug。
3. 作为读模板的人，我想要一份"不写在这里的东西"的清单，这样我知道缩进、命名、"要写测试"该去哪。
4. 作为读模板的人，我想要每条规则写清谁在强制，这样我知道哪些建检查、哪些靠 review。
5. 作为模板使用者，我想要一份"这份文件怎么变长"的维护机制，这样第一天之后我还知道怎么养它。
6. 作为模板使用者，我想要它说清规范只该有 5–15 条，这样我不会写成没人读的长文档。
7. 作为第一次打开这个仓库的人，我想要 README 直接告诉我有这些模板，这样我不用浏览目录树才能发现。
8. 作为第一次打开这个仓库的人，我想要知道这些**不是** Matt Pocock skill 的内容，这样我不会误归因。
9. 作为第一次打开这个仓库的人，我想要知道这些**不是**本仓库自身的规范，这样我不会以为这是个代码项目。
10. 作为维护者，我想要模板放在翻译桶之外，这样上游同步不会碰到它们。
11. 作为维护者，我想要 `verify_zh.py` 在加了模板之后仍然全绿，这样桶内对齐不被破坏。
12. 作为维护者，我想要 AGENTS.md 里"唯一产出物"的说法保持成立，这样后续智能体不困惑。
13. 作为后续智能体，我想要一页 wiki 记录为什么放仓库根，这样我不会日后"顺手修正"它的位置。
14. 作为后续智能体，我想要决策页写明模板违反了它自己的第 3 条规则，这样我不会把它当成 bug 去"修"。
15. 作为要抄 Python 版的人，我想要例子用 Python 惯用形态（`dataclass`、`monkeypatch`、pytest fixture），这样规则能对上我真在用的工具。
16. 作为要抄 Java 版的人，我想要例子用 Java 惯用形态（Builder、ArchUnit、Testcontainers），理由同上。
17. 作为要抄 TypeScript 版的人，我想要例子用 TS 惯用形态（dependency-cruiser、oxlint），理由同上。
18. 作为要在三个语言版本之间切换的人，我想要它们共用同一套骨架，这样换个语言不用重新学格式。
19. 作为从索引 README 挑文件的人，我想要一眼看到各版本的工具链，这样我能快速选对文件。
20. 作为担心准确性的读者，我想要索引 README 顶部就有警示，这样我在抄第一行之前就看到前提。
21. 作为搜索本仓库的人，我想要"编码规范"这类关键词能命中 README，这样我不用记得目录名。
22. 作为维护者，我想要新增的目录不出现在桶内对齐的错误信息里，这样同步报告不被噪音淹没。

## Implementation Decisions

- **位置：仓库根 `CODING_STANDARDS/`**，不放 `docs/`。理由是 `AGENTS.md` 把 `docs/` 定义为
  「元数据，不属于产出物」，而这三份是供人拷走使用的实体内容，性质上是产出物。
- **目录名用全大写**，与上游 `CODING_STANDARDS.md` 的命名习惯一致；文件名只留语言后缀
  （`typescript.md` / `python.md` / `java.md`），因为拷进项目时要改名成 `CODING_STANDARDS.md`。
- **保留示例事故并显式标注**，而不是全部换成占位符（三个候选方案中的 B）。
  理由：这套规范的说服力来自具体事故细节，抽空细节就退化成它自己批评的「通用建议」。
  代价已知——模板违反了它自己的第 3 条规则，这是有意取舍，写在索引 README 顶部。
- **不属于译文产出物**。`AGENTS.md` 的「唯一产出物」改为「唯一**译文**产出物」，否则
  加了新目录后该说法不成立。同时登记新目录并写明"不是本仓库自身的规范"。
- **不参与桶内对齐**，`verify_zh.py` 与 `deploy_zh.py` 都不遍历它。
- **全局 README 的位置在「装到本地」之后**，作为独立一节；「目录结构」代码块同步加一行。
  用户选择了靠前而非「目录结构」之后，理由是这些是给人用的东西。
- **三个语言版本共用同一套骨架**：祈使句标题 + 为什么 + `Enforced by`，
  外加同一份"不写什么"表和"怎么变长"机制。跨语言不变的是判断题，变的只是工具链那一列。
- **索引 README 承担三件事**：目录导航、使用姿势（5–15 条上限、先过判据）、以及事故是示例的警示。

## Testing Decisions

**什么算好的测试**：只测外部可观察的行为，不测实现细节。放到这个仓库，
就是测"加了目录之后，仓库的机械不变量仍然成立"，而不是测模板内容写得好不好
——后者没有可断言的外部行为。

**实际的接缝**：

- `python scripts/verify_zh.py` —— 唯一的自动化接缝。它管四桶对齐、frontmatter、
  协议字符串、死链、README 数字。加 `CODING_STANDARDS/` 不该让它变红。
- `python scripts/deploy_zh.py` —— 安装位漂移，同样不该受影响。
- 死链检查 —— README 与 wiki 里的相对链接必须能解析。

**既有先例**：同一天早些时候，`verify_zh.py` 加过死链与 README 数字检查（`d1751ed`），
四条回归测试都验证过"注入错误会红"。本 spec 的验证沿用同一套做法。

**发现的缺口**：`verify_zh.py` **不覆盖** `CODING_STANDARDS/` 的内容——
它只在死链检查里被扫到链接，模板正文的规则质量没有任何机械保护。
这是有意的（模板内容是给人读的，没有可断言的性质），但意味着：
**模板里的示例事故若被误当成真实事故传播出去，没有任何检查会拦。**
两层人工警示（每条标注 + 顶层说明）是唯一防线。

**本次验证实际做过**：
- `verify_zh.py` 全绿（含死链 145 条、README 数字一致）
- `deploy_zh.py` 漂移 0
- 新文件的相对链接逐条解析
- 提交时 pre-commit 钩子跑了完整校验

## Out of Scope

- **把示例事故换成真实事故**。那需要一个真在用这些规范的代码项目；本仓库是文档项目。
- **Rust / Go / 其他语言版本**。用户只要了三个。
- **在一个真实代码项目里落地验证**。未做。
- **issue tracker 配置**。`to-spec` 要求发布到 tracker 并打 `ready-for-agent`，
  本仓库没有 tracker，故未执行该步骤。
- **让模板内容受机械检查保护**。见 Testing Decisions 的缺口说明。
- **上游 `mattpocock/skills` 的对应改动**。这些模板是本仓库独立产出，不回流上游。

## Further Notes

- **这份规格是事后补的**，因此它无法起到"动手前把关"的作用。它现在的价值是：
  （a）让用户比对"原意"与"实做"，看到不一致还能改；（b）留档，下次问
  "为什么放仓库根"时有据可查。
- **接缝偏弱**。真正的守门员是 `verify_zh.py`，但它对模板正文无能为力。
  如果将来这批模板要长期维护，值得考虑加一条检查：索引 README 里的文件名必须
  与目录下的实际文件一致。这条现在没做。
- **spec 本身的定位问题**：`to-spec` 的流程是"规格 → 实现"，它假设规格是实现的输入。
  事后补的规格不是输入而是对照物，两者的用途不同。下次再有同类工作，
  应该在动手前先出规格。
