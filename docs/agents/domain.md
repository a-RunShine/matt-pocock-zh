# 领域文档

工程类 skill 在探索代码库时，应当如何使用本仓库的领域文档。

本仓库是**单上下文**布局：仓库根一个 `GLOSSARY.md`，加 `docs/adr/`。

## 探索之前，先阅读这些

- 仓库根目录的 **`GLOSSARY.md`**
- **`docs/adr/`**：阅读涉及你即将工作的区域的 ADR

如果这些文件中有任何一个不存在，就**静默继续**。不要指出它们的缺失，也不要预先建议创建它们。`/domain-modeling` skill（通过 `/grill-with-docs` 和 `/improve-codebase-architecture` 调用）会在术语或决定真正被确定时才惰性地创建它们。

本仓库此刻两者都还没有。它们会在需要时被创建，不要为了"结构完整"先建空壳。

## 文件结构

```
/
├── GLOSSARY.md
├── docs/adr/
│   ├── 0001-<决定>.md
│   └── 0002-<决定>.md
└── docs/
```

如果将来根目录出现 `GLOSSARY-MAP.md`，布局改为多上下文：`GLOSSARY-MAP.md` 指向各上下文自己的 `GLOSSARY.md`，ADR 分系统级（`docs/adr/`）与上下文级（`<context>/docs/adr/`）。

## 使用术语表中的词汇

当你的输出提到某个领域概念（在 issue 标题、重构提案、假设或测试名称中）时，使用 `GLOSSARY.md` 中定义的术语。不要滑向术语表明确避免的同义词。

如果你需要的概念尚未出现在术语表中，这就是一个信号：要么你在发明项目并不使用的语言（重新考虑），要么确实存在缺口（记下来，留给 `/domain-modeling`）。

本仓库另有一份跨文件术语约定在 `docs/wiki/rules/2026-10-27-terminology.md`，管的是**译文用词**（skill、智能体、接缝这类），与领域概念不冲突但同属"用词一致"的约束。翻译相关的产出以它为准。

## 标记 ADR 冲突

如果你的输出与某个现有 ADR 相矛盾，应明确指出，而不是悄悄覆盖：

> _与 ADR-0007（事件溯源的订单）相矛盾，但值得重新审视，因为……_
