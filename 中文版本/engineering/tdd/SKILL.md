# 测试驱动开发（TDD）

TDD 就是红 → 绿的循环。本 skill 是让这个循环产出值得保留的测试的参考：什么是好的测试、测试应放在哪里、反模式，以及循环的规则。每一节都适用于每一次循环：在循环之前和之中参考它们，而不是事后再看。

探索代码库时，如果存在 `GLOSSARY.md`，请阅读它，使测试名称和接口术语与项目的领域语言保持一致，并尊重你所涉及领域的 ADR。

## 什么是好的测试

测试应通过公共接口验证行为，而不是实现细节。代码可以完全改变，测试不应改变。好的测试读起来像一份规格说明："用户可以用有效的购物车完成结账"准确地告诉你存在什么能力，而且它能经受住重构，因为它不关心内部结构。

示例参见 [tests.md](tests.md)，mock 指南参见 [mocking.md](mocking.md)。

## 接缝：测试应放在哪里

**接缝（seam）**是你测试所在的公共边界：你可以在不深入内部的情况下观察行为的接口。测试只存在于接缝处，绝不针对内部实现。

**只在预先约定的接缝处测试。** 在编写任何测试之前，先写下要测试的接缝，并与用户确认。没有经过确认的接缝，就不写测试。你不可能测试所有东西，因此预先约定接缝，正是让测试精力落在关键路径和复杂逻辑上，而不是每一个边缘情况上的方式。

要问的问题："公共接口是什么？我们应该测试哪些接缝？"对每个提议的接缝，用一行说明它能抓住什么、会漏掉什么。

当该接口本身的形态存在疑问时（模块有多深、接缝应放在哪里、接口应暴露什么），调用 Skill 工具并传入 "codebase-design" 以获取词汇。它是模块、接口、深度、接缝、适配器、杠杆和局部性等术语的共同来源，是需要查阅的参考，而不是需要运行的会话。

## 反模式

- **与实现耦合**：mock 内部协作者、测试私有方法，或通过旁路验证（例如直接查询数据库，而不是使用接口）。判断依据：重构后测试会失败，而行为并没有改变。
- **同义反复（Tautological）**：断言用与代码相同的方式重新算出预期值（`expect(add(a, b)).toBe(a + b)`、以同样方式手算出的快照、把一个常量断言为等于它自己），因此它依照构造必然通过，永远不可能与代码产生分歧。预期值必须来自独立的真实来源：一个已知正确的字面量、一个已算好的示例，或规格说明。
- **水平切片**：先写完所有测试，再写完所有实现。成批的测试验证的是_想象中的_行为：你测试的是事物的_形态_，而不是面向用户的行为；测试会对真实的变化变得迟钝，并且在还不了解实现之前就锁定了测试结构。应改为以**纵向切片**工作：一个测试 → 一个实现 → 重复，每个测试都是一颗**曳光弹（tracer bullet）**，会响应上一轮循环所学到的东西。

## 循环规则

- **先红后绿。** 先写失败的测试，然后只写足以通过它的代码。不要预先考虑未来的测试，也不要添加投机性的功能。
- **一次一个切片。** 每一轮循环只有一个接缝、一个测试、一个最小实现。
- **重构不属于循环的一部分。** 它属于评审阶段（参见 `code-review` skill），而不属于红 → 绿的实现循环。
