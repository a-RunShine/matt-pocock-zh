# 深化

给定一组浅层模块的依赖关系，如何安全地深化它们。假设读者已掌握 [SKILL.md](SKILL.md) 中的词汇：**模块**、**接口**、**接缝**、**适配器**。

## 依赖类别

在评估一个深化候选项时，先对它的依赖进行分类。类别决定了深化后的模块如何跨越其接缝进行测试。

### 1. 进程内（In-process）

纯计算、内存状态，没有 I/O。总是可以深化：合并模块，并直接通过新接口进行测试。不需要适配器。

### 2. 本地可替代（Local-substitutable）

具有本地测试替身的依赖（用于 Postgres 的 PGLite、内存文件系统）。如果替身存在，就可以深化。深化后的模块在测试套件中用该替身运行。接缝是内部的；模块的外部接口上没有端口。

### 3. 远程但自有（Remote but owned，端口与适配器）

你自己拥有、跨越网络边界的服务（微服务、内部 API）。在接缝处定义一个**端口**（接口）。深层模块拥有逻辑；传输层作为**适配器**被注入。测试使用内存适配器。生产环境使用 HTTP/gRPC/队列适配器。

推荐形式："在接缝处定义一个端口，为生产环境实现 HTTP 适配器，为测试实现内存适配器，使逻辑即使跨网络部署，也只存在于一个深层模块中。"

### 4. 真正的外部依赖（Mock）

你无法控制的第三方服务（Stripe、Twilio 等）。深化后的模块把外部依赖作为注入的端口接收；测试提供 mock 适配器。

## 接缝纪律

- **一个适配器意味着假设性的接缝；两个适配器才是真正的接缝。** 除非至少有两个适配器是合理的（通常是生产环境加测试），否则不要引入端口。只有一个适配器的接缝只是间接层。
- **内部接缝与外部接缝。** 深层模块可以有内部接缝（仅对其实现可见，由它自身的测试使用），也可以在接口处有外部接缝。不要仅仅因为测试在用，就把内部接缝通过接口暴露出来。

## 测试策略：替换，而非叠加

- 一旦深化后模块的接口处存在测试，浅层模块上的旧单元测试就变成了废物；删除它们。
- 在深化后模块的接口处编写新测试。**接口即测试表面。**
- 测试通过接口断言可观察的结果，而不是内部状态。
- 测试应当能经受内部重构，因为它们描述的是行为，而不是实现。如果实现变化时测试必须跟着变化，那说明它测试的是接口之外的东西。
