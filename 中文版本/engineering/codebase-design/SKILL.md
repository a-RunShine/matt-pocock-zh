# 代码库设计

设计**深层模块**：在一个小接口背后蕴含大量行为，放置在一个干净的接缝处，并能通过该接口进行测试。在任何设计或重构代码的地方，都使用这套语言和这些原则。目标是：为调用者带来**杠杆**，为维护者带来**局部性**，为所有人带来**可测试性**。

## 术语表

准确使用这些术语：不要替换为"组件"、"服务"、"API"或"边界"。统一的语言正是其意义所在。

**模块（Module）**：任何同时具有接口和实现的东西。它刻意与尺度无关：可以是一个函数、类、包，或跨层的切片。_Avoid_：unit、component、service。

**接口（Interface）**：调用者为了正确使用该模块所必须知道的一切：类型签名，但也包括不变量、顺序约束、错误模式、所需配置以及性能特征。_Avoid_：API、signature（范围太窄，只指类型层面的表面）。

**实现（Implementation）**：模块内部的东西，即其代码主体。区别于**适配器（Adapter）**：一个东西可以是一个体量小的适配器却有很大的实现（例如一个 Postgres 仓储），也可以是一个体量大的适配器却只有很小的实现（例如一个内存中的假实现）。当话题是接缝时，使用"适配器"；否则使用"实现"。

**深度（Depth）**：在接口处的杠杆。调用者（或测试）每学习一单位的接口，就能行使的行为量。当大量行为位于一个小接口之后时，模块是**深的**；当接口几乎与实现一样复杂时，模块是**浅的**。

**接缝（Seam）**（Michael Feathers 提出）：一个可以在不编辑其所在位置的情况下改变行为的地方；模块接口所在的**位置**。接缝应放在哪里，是一个独立的设计决定，区别于放在它后面的内容。_Avoid_：boundary（与 DDD 的有界上下文混淆）。

**适配器（Adapter）**：在接缝处满足某个接口的具体事物。它描述的是*角色*（它填补哪个槽位），而不是*实质*（其内部是什么）。

**杠杆（Leverage）**：调用者从深度中获得的东西。每学习一单位的接口，获得更多的能力。一个实现可以回报 N 个调用点和 M 个测试。

**局部性（Locality）**：维护者从深度中获得的东西。变更、bug、知识和验证都集中在一处，而不是散布在调用者之间。修复一次，处处生效。

## 深层与浅层

**深层模块** = 小接口 + 大量实现：

```
┌─────────────────────┐
│   Small Interface   │  ← 方法少，参数简单
├─────────────────────┤
│                     │
│  Deep Implementation│  ← 复杂逻辑被隐藏
│                     │
└─────────────────────┘
```

**浅层模块** = 大接口 + 少量实现（应避免）：

```
┌─────────────────────────────────┐
│       Large Interface           │  ← 方法多，参数复杂
├─────────────────────────────────┤
│  Thin Implementation            │  ← 只是原样传递
└─────────────────────────────────┘
```

设计接口时，问自己：

- 我能减少方法的数量吗？
- 我能简化参数吗？
- 我能把更多复杂性藏在内部吗？

## 原则

- **深度是接口的属性，而不是实现的属性。** 深层模块在内部可以由小型、可 mock、可替换的部件组成；它们只是不属于接口的一部分。模块既可以有**内部接缝**（仅对其实现可见，由其自身的测试使用），也可以在接口处有**外部接缝**。
- **删除测试。** 设想删除这个模块。如果复杂性随之消失，它就是一个直通层。如果复杂性在 N 个调用者中重新出现，那它就是在物有所值地存在。
- **接口即测试表面。** 调用者和测试穿过的是同一个接缝。如果你想测试接口*之外*的东西，那么这个模块很可能形态不对。
- **一个适配器意味着假设性的接缝；两个适配器才是真正的接缝。** 除非确实有东西会在某个接缝两侧发生变化，否则不要引入接缝。

## 为可测试性而设计

好的接口让测试变得自然：

1. **接受依赖，而不是自己创建依赖。**

   ```typescript
   // 可测试
   function processOrder(order, paymentGateway) {}

   // 难以测试
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，而不是产生副作用。**

   ```typescript
   // 可测试
   function calculateDiscount(cart): Discount {}

   // 难以测试
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **表面积小。** 方法越少，需要的测试越少。参数越少，测试的搭建越简单。

## 关系

- 一个**模块**恰好拥有一个**接口**（它向调用者和测试所呈现的表面）。
- **深度**是**模块**的属性，以其**接口**来衡量。
- **接缝**是**模块**的**接口**所在之处。
- **适配器**位于**接缝**处，并满足**接口**。
- **深度**为调用者产生**杠杆**，为维护者产生**局部性**。

## 被否决的说法

- **以实现行数与接口行数之比来衡量深度**（Ousterhout 的做法）：这会奖励给实现注水。我们改用"深度即杠杆"。
- **把"接口"理解为 TypeScript 的 `interface` 关键字或类的公开方法**：范围太窄。这里的接口包括调用者必须知道的每一个事实。
- **"边界（Boundary）"**：与 DDD 的有界上下文混淆。应说**接缝**或**接口**。
