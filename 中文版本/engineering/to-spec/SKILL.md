本 skill 利用当前对话上下文和对代码库的理解来产出一份规格说明。不要访谈用户；只综合你已经掌握的内容。

issue tracker 和分诊标签词汇应已提供给你。如果没有，就告诉用户运行 `/setup-matt-pocock-skills`。

## 流程

1. 如果你还没有探索过，就先浏览仓库，了解代码库的当前状态。在整个规格说明中使用项目领域术语表的词汇，并尊重你所涉及领域的任何 ADR。

2. 勾勒出你将用来测试该功能的**接缝（seam）**。优先使用已有的接缝，而不是新建。尽可能使用最高层的接缝。如果确实需要新接缝，就在你能找到的最高层级提出。整个代码库中的接缝越少越好，理想数量是一个。

请与用户确认这些接缝是否符合他们的预期。

3. 使用下方模板撰写规格说明，然后发布到项目的 issue tracker。应用 `ready-for-agent` 分诊标签，无需额外分诊。

<spec-template>

## Problem Statement

用户所面临的问题，从用户的视角描述。

## Solution

针对该问题的解决方案，从用户的视角描述。

## User Stories

一份很长的编号用户故事列表。每个用户故事的格式为：

1. 作为<角色>，我希望<功能>，以便<收益>

<user-story-example>
1. 作为一名手机银行客户，我希望能看到我各账户的余额，以便我能更明智地安排开支
</user-story-example>

这份用户故事列表应当极其详尽，覆盖该功能的所有方面。

## Implementation Decisions

已做出的实现决策列表。可以包括：

- 将被构建或修改的模块
- 那些将被修改的模块的接口
- 开发者提出的技术澄清
- 架构决策
- Schema 变更
- API 契约
- 具体的交互方式

不要包含具体的文件路径或代码片段。它们很快就会过时。

例外：如果某个原型产生的代码片段比成段文字更精确地编码了某项决策（状态机、reducer、schema、类型形状），就将其内联到相关决策中，并简要注明它来自原型。只保留包含关键决策的部分，修剪掉可运行的演示，只留下重要的核心。

## Testing Decisions

已做出的测试决策列表。包括：

- 对什么是好测试的描述（只测试外部行为，不测试实现细节）
- 将被测试的模块
- 测试的既有依据（即代码库中类似类型的测试）

## Out of Scope

本规格说明明确不包含的内容的描述。

## 补充说明

关于该功能的任何其他补充说明。

</spec-template>
