围绕 `HEAD` 与用户提供的某个固定基准点之间的 diff 进行双轴评审：

- **规范（Standards）**：代码是否符合本仓库的已有编码规范？
- **规格（Spec）**：代码是否忠实地实现了源 issue/规格说明？

两个维度都以**并行子智能体**的方式运行，使它们的上下文互不污染，然后由本 skill 汇总它们的发现。

issue tracker 应已提供给你。如果没有，就告诉用户运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 确定基准点

用户所说的任何内容都是基准点（提交 SHA、分支名、标签、`main`、`HEAD~5` 等）。如果用户没有指定，就询问。

只捕获一次 diff 命令：`git diff <fixed-point>...HEAD`（使用三点语法，因此比较的是与 merge-base 的对比）。同时记录提交列表：`git log <fixed-point>..HEAD --oneline`。

在继续之前，确认基准点能够解析（`git rev-parse <fixed-point>`），并且 diff 非空。无效的引用或空的 diff 应当在这里就失败，而不是在两个并行子智能体内部才失败。

### 2. 确定规格来源

按以下顺序查找源规格说明：

1. 提交信息中的 issue 引用（`#123`、`Closes #45`、GitLab 的 `!67` 等），通过 tracker 文档中的流程获取。
2. 用户作为参数传入的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名或功能匹配的规格文件。
4. 如果什么都没找到，询问用户规格在哪里。如果用户说没有规格，那么**规格**子智能体将跳过，并报告"无可用规格"。

### 3. 确定规范来源

在仓库中搜索所有记录了代码应当如何编写的文件。如果存在 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`，它必须列入清单。

除了仓库记录的内容之外，规范维度始终携带**坏味道基线（smell baseline）**：一组固定的 Fowler 代码坏味道（_Refactoring_ 第 3 章），即使仓库什么都没有记录，它也适用。两条规则约束它：

- **仓库优先。** 仓库记录的标准始终优先；如果它认可了基线会标记的某种做法，就压制该坏味道。
- **始终是判断性的。** 每种坏味道都是一条带标签的启发式（"可能存在 Feature Envy"），绝不是硬性违规。和本 skill 中的其他标准一样，跳过工具已经强制执行的内容。

每种坏味道的描述格式为：*它是什么* → *如何修复*；将其与 diff 进行比对：

- **Mysterious Name（神秘的名字）**：函数、变量或类型的名字没有揭示它做什么或持有什么。→ 重命名；如果想不出一个诚实的名字，说明设计本身还模糊。
- **Duplicated Code（重复代码）**：同样的逻辑形状出现在变更中的多个代码块或文件里。→ 抽取共享的形状，并在两处调用它。
- **Feature Envy（依恋情结）**：一个方法访问其他对象的数据比访问自己的数据还多。→ 把该方法移动到它所依恋的数据所在之处。
- **Data Clumps（数据泥团）**：同样的几个字段或参数总是一起出现（应当诞生一个类型）。→ 把它们打包成一个类型，改为传递该类型。
- **Primitive Obsession（基本类型偏执）**：一个基本类型或字符串代替了一个值得拥有自己类型的领域概念。→ 为该概念赋予一个小型的专属类型。
- **Repeated Switches（重复的 Switch）**：同一类型上的同一个 `switch`/`if` 级联在变更中多次出现。→ 用多态替代，或用一个两处共享的映射。
- **Shotgun Surgery（散弹式修改）**：一次逻辑变更迫使在 diff 中的许多文件里进行零散的编辑。→ 把一起变化的东西收拢到一个模块中。
- **Divergent Change（发散式变化）**：一个文件或模块因多个互不相关的原因被修改。→ 拆分，使每个模块只因一个原因而变化。
- **Speculative Generality（夸夸其谈的通用性）**：为规格并不需要的需求而添加的抽象、参数或钩子。→ 删除它；在出现真实需求之前，把它内联回去。
- **Message Chains（过长的消息链）**：调用者不应依赖的长链式导航 `a.b().c().d()`。→ 在第一个对象上提供一个方法，把这段遍历隐藏在其后。
- **Middle Man（中间人）**：一个类或函数大部分时间只是把调用委派下去。→ 删掉它，直接调用真正的目标。
- **Refused Bequest（拒绝的遗赠）**：一个子类或实现者忽略或覆盖了它继承的大部分内容。→ 去掉继承，改用组合。

### 4. 并行启动两个子智能体

在前台同时发起两个子智能体的调用，并汇总它们返回的报告。

**规范子智能体的提示词**应包括：

- 完整的 diff 命令和提交列表。
- 你在第 3 步中找到的规范来源文件列表，**以及第 3 步中的完整坏味道基线**（子智能体无法访问其他内容，因此必须把它全文粘贴进来）。
- 任务说明："按文件/代码块（如相关）报告：(a) diff 中每一处违反已记录规范的地方：引用该规范（文件 + 规则）；(b) 你发现的任何基线坏味道：指出它并引用对应代码块。区分硬性违规与判断性问题：违反已记录规范可以是硬性的，但基线坏味道始终是判断性的，且仓库记录的规范优先于基线。跳过工具已强制执行的内容。不超过 400 字。"

**规格子智能体的提示词**应包括：

- diff 命令和提交列表。
- 规格的路径或获取到的内容。
- 任务说明："报告：(a) 规格要求但缺失或仅部分实现的需求；(b) diff 中未被要求的行为（范围蔓延）；(c) 看似已实现、但实现看起来有误的需求。为每项发现引用规格中的对应行。不超过 400 字。"

如果规格缺失，就跳过规格子智能体，并在最终报告中注明这一点。

### 5. 汇总

以 `## Standards` 和 `## Spec` 两个标题分别呈现两份报告，原样或略作整理。**不要**合并或重新排序发现，因为两个维度是刻意分开的（参见*为什么要两个维度*）。

最后用一行做总结：每个维度的发现总数，以及*每个维度内部*最严重的问题（如果有）。不要在维度之间挑出一个单一的"赢家"：那正是分开所要防止的重新排序。

## 为什么要两个维度

一项变更可能通过一个维度，却在另一个维度上失败：

- 遵循了所有规范，却实现了错误的东西 → **规范通过，规格失败。**
- 完全按照 issue 的要求做了，却破坏了项目的约定 → **规格通过，规范失败。**

分开报告，可以防止一个维度掩盖另一个维度。
