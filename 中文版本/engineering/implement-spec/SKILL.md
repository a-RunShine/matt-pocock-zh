你已经拿到一份规格说明。这份规格说明应当关联有工单，描述了如何实现该规格说明。

issue tracker 应已提供给你。如果没有，就告诉用户运行 `/setup-matt-pocock-skills`。

目标是整份规格都在一条**集成分支**上实现，并且每张工单都以 issue tracker 关闭工作的方式完成。

这些工单并不是步骤清单，而是一张带有阻塞关系的**任务图**。这意味着总会存在一个可以立即领取的工单**前沿（frontier）**。

与子智能体之间的沟通应当精简。主要通过**上下文指针**进行沟通：指向规格说明、工单、研究笔记和先前的提交。不要重复那些已经可以通过指针获取的信息。

**实现者子智能体**应尽可能在后台运行，以实现**最大并发**。

## 步骤

1. 阅读规格说明和工单，理解任务图。

2.（可选）使用一个**探索子智能体**，完成工单所要求的任何探索，例如相关的代码库文件或外部文档。确保探索子智能体能够保存文件：它应当将其 markdown 笔记保存在仓库之外的一个目录中，供所有后续子智能体访问。这让**实现者子智能体**可以专注于实现，而不必再去探索。

3. 创建集成分支。如果 issue tracker 通过 PR 关闭工作，或者用户要求提交 PR，就在第 5 步完成第一次合并之后，开启一个草稿 PR（一个相对 main 没有新提交的分支无法开启 PR），并标注它会关闭该规格说明和工单。

4. 使用**实现者子智能体**来实现每一张工单，每个都在自己的 worktree 中、位于自己的分支上工作。每个实现者子智能体：
   - 在开始之前确认其 worktree 基于集成分支；如果不是，就重置到集成分支上；
   - 调用 Skill 工具并传入 `tdd` 来构建该工单；
   - 在报告完成之前，把集成分支的最新提交合并进它自己的分支。

5. 一旦某个**实现者子智能体**完成，就用一个**合并者子智能体**把它的工作合并到集成分支。

6. 如果这改变了可用工单的**前沿**，就启动更多**实现者子智能体**来处理新的工单。这样可以实现最大并发。

7. 所有工单完成后，在集成分支上调用 Skill 工具并传入 `code-review`。用一个**实现者子智能体**修复代码评审提出的所有问题。

8. 如果存在草稿 PR，就将其标记为可供评审。否则，以 issue tracker 关闭工作的方式解决每张工单，并报告集成分支。

9. 清理所有**实现者子智能体**的 worktree。
