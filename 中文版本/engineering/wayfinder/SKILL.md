一个模糊的想法出现了，它大到一个智能体会话装不下，并且被迷雾笼罩：通往**目的地（destination）**的路径还看不见。寻路（wayfinding）的目的是找到这条路，而不是直接冲向目的地。本 skill 会把这条路绘制成 issue tracker 上的一张**共享地图**，然后逐一处理其中的**决策工单**（即其解决方式是一个决定、而不是待执行的构建切片的问题），直到路线清晰。

目的地因每个工作而异，明确它是绘图的第一步，它会影响每一张工单。目的地可能是一份可供交接并持续迭代的规格说明，也可能是在规划开始前需要锁定的一项决定，或是原地完成的一项变更（例如一次数据结构迁移）。这张地图与领域无关：工程工作、课程内容，或任何符合这种形态的事物都可以。

## 只规划，不执行

寻路默认是**规划**：每张工单解决一个决定，当路线清晰、无需再做决定即可交由他人去执行时，地图就完成了。想直接去做工作的冲动，通常意味着你已经走到地图的边缘，是时候交接了。只有当某个工作在其**备注（Notes）**中特别声明时，才可以把执行带入地图本身；否则，只产出决定，而不是交付物。

## 用名称来指代

每张地图和每张工单都是一个 issue，因此都有一个**名称**：也就是它的标题。在人类会阅读的一切内容中（叙述、地图的"已做出的决定"），都要用名称来指代它，绝不使用裸的 id、编号或 slug。满屏的 `#42, #43, #44` 难以辨认；名称一眼就能读懂。id 和 URL 并不会消失；名称包裹着链接，而 id 和 URL 是_蕴含在_名称之中的，它们绝不能取代名称。

## 地图（The Map）

地图是本仓库 issue tracker 上的一个 issue，带有 `wayfinder:map` 标签，是规范的产物。它的工单是地图的子 issue。

地图是一个**索引**，而不是一个存储库。它列出已做出的决定，并指向承载其细节的工单；一个决定只存在于唯一一个地方，即它的工单，因此地图从不重复陈述决定的内容，只给出摘要并附上链接。

**地图、其子工单、阻塞关系以及前沿查询在物理上位于何处，取决于具体的 tracker。** 工具应已为你提供 issue tracker。如果没有，就告诉用户运行 `/setup-matt-pocock-skills`。请查阅 tracker 文档中的"寻路操作（Wayfinding operations）"一节，了解_本仓库_如何表达这些操作。如果没有提供任何 tracker，则默认使用本地 markdown tracker。

### 地图正文

整张地图的低分辨率视图，每个会话加载一次。未关闭的工单不列在这里：它们是未关闭的子 issue，通过查询找到。

```markdown
## Destination

<通过完成本地图，所要抵达的终点是什么样子：本次工作正在寻找的规格说明、决定或变更。一到两行；每个会话在选择工单之前都要先对照它定位方向。>

## Notes

<领域；每个会话都应参考的 skill；本次工作的常规偏好>

## Decisions so far

<!-- 索引：每张已关闭的工单占一行，足以判断相关性，然后点击链接查看工单所承载的详细内容 -->

- [<已关闭工单的标题>](链接)：<答案的一行摘要>

## Not yet specified

<!-- 参见"战争迷雾"：范围之内、但还无法建立工单的迷雾；随着前沿推进而毕业 -->

## Out of scope

<!-- 参见"范围之外"：被划在目的地之外的工作；已关闭，不会毕业 -->
```

### 工单

每张工单都是地图的一个**子 issue**；tracker 的 issue id 就是它的身份标识。它的正文是问题本身，大小以一个 100K token 的智能体会话为限：

```markdown
## 问题

<本工单要解决的决定或调查>
```

每张工单都带有一个 `wayfinder:<type>` 标签，取值为 `research`、`prototype`、`grilling`、`task` 之一（参见[工单类型](#工单类型)）。`wayfinder:` 标签是地图及其工单唯一会带的标签，绝不带有 `ready-for-agent` 之类的分诊标签：它们是决定，而不是实现工作。

会话在做任何工作之前，**首先**将工单分配给推动该地图的开发者，以此**认领**它，使并发会话跳过它。这个分配者_就是_认领：一个开放且未分配的工单才是未认领的。

阻塞关系使用 tracker **原生的**依赖关系：这一点至关重要，因为它能在 tracker 自身的 UI 中直观地渲染出前沿，使人类无需打开地图就能看到哪些工作可以接手。只有缺少原生阻塞功能的 tracker 才会退而使用正文约定。当一张工单所阻塞的所有工单都已关闭时，它即为**未被阻塞（unblocked）**；**前沿（frontier）**就是那些开放、未被阻塞、未被认领的子工单，即已知世界的边缘。

答案不属于正文的一部分；它在解决时被记录（参见[推进地图](#推进地图)）。在解决某张工单的过程中创建的资产，从该 issue 中链接过去，而不是粘贴进来。

## 工单类型

每张工单要么是 **HITL**（human in the loop，与一位能为自己发言的人类一同完成），要么是 **AFK**，由智能体独自驱动。HITL 工单只能通过这种现场交流来解决；智能体绝不能代替人类一方来回答（一个自己回答自己问题的拷问型智能体，就违反了这一点）。

- **研究（Research）**（AFK）：阅读文档、第三方 API 或本地资源（如知识库），以找出某个决定所依赖的事实。由一个子智能体调用 Skill 工具并传入 "research" 来解决。当需要当前工作目录之外的知识时使用。
- **原型（Prototype）**（HITL）：通过制作一个廉价、粗糙、具体的产物供人反应，以提高讨论的保真度（一个大纲、一个粗略的想法、一个桩代码，或 UI/逻辑代码），调用 Skill 工具并传入 "prototype"。将原型链接为一项资产。当关键问题是"它应该长什么样"或"它应该怎样运作"时使用。
- **拷问（Grilling）**（HITL）：对话。这是默认情况。始终调用两次 Skill 工具，分别传入 "grilling" 和 "domain-modeling"。
- **任务（Task）**（HITL 或 AFK）：在做出_决定_之前必须完成的手工工作：没有需要决定、原型化或研究的内容，但讨论因它未完成而受阻。例如注册服务以便评估其 API、开通访问权限、迁移数据以便看清其结构。这是唯一_去做_而不是_去决定_的类型，它的价值在于解除某个决定的阻塞，而不是交付目的地本身。如果智能体可以独自完成，就由它驱动（AFK）；否则，就向人类交付一份精确的清单（HITL）。当工作完成时即解决；答案需记录所做的事情，以及后续工单所依赖的任何结果性事实（凭证位置、新的 URL、行数）。

## 战争迷雾

地图是_刻意_不完整的：不要绘制你还看不清的部分。在现有工单之外，是**战争迷雾**：对于那些你能够判断即将到来、却还无法精确界定的决定和调查，所呈现的模糊视图，因为它们取决于仍然悬而未决的问题。解决一张工单，会清除其前方的迷雾，把现在已能明确界定的部分毕业为新的工单，一次一张，直到通往目的地的路径清晰，且不再剩余工单。

地图的 **尚未明确的部分（Not yet specified）** 一节，就是记录这种模糊视图的地方：怀疑的问题、以后需要重新审视的区域。它是通往目的地的、尚未被发现的前沿：这里的一切都在范围之内，只是还不够清晰、无法建立工单。写得粗略或详细都可以，视视图的清晰程度而定；它同时也是协作者阅读时了解工作走向的路标。

**迷雾还是工单？** 判断标准是你现在能否精确地陈述这个问题，而_不是_你现在能否回答它。

- **当问题已经足够清晰时，建立工单**，即使它被阻塞、你现在还无法行动。
- **当你还无法把问题表述得这么清晰时，放入尚未明确的部分。** 不要把迷雾预先切分成工单大小的碎片：它比工单粗，一块补丁在前沿抵达时，可能毕业为若干工单，也可能一张都不生成。

**尚未明确的部分**不包括已经做出的决定（已做出的决定）、已经存在的活跃工单，以及范围之外的内容（下一节）。

## 范围之外

迷雾只会朝目的地汇聚。目的地决定了范围，因此超出目的地的工作属于**范围之外**：它不是迷雾，也不属于**尚未明确的部分**。它在地图上有自己的 **范围之外（Out of scope）** 一节：你有意识地排除在_本次_工作之外的工作。范围，而不是清晰度，决定了它落在这里。

范围之外的工作永远不会毕业（前沿止于目的地），因此只有在目的地被重新划定时才会回归，而且是作为一项新的工作，而不是对原工作的延续。

将某件事排除在范围之外，是一个界定范围的行为，而不是路线上的一步。当一张已经存在的工单结果超出了目的地（在绘图时错误地纳入，或在某次解决中被暴露出来），就**关闭它**（已关闭的工单明确地离开了前沿），并在 **范围之外** 一节中留下一行：摘要加上排除的理由，并链接到已关闭的工单。它不会出现在 **已做出的决定** 中，因为后者记录的是实际走过的路线；划定范围的边界不是路线上的一步。

## 调用方式

有两种模式。无论哪种，**每个会话绝不解决超过一张工单**，研究工单除外。

### 绘制地图

用户以一个模糊的想法来调用。

1. **命名目的地。** 调用两次 Skill 工具，分别传入 "grilling" 和 "domain-modeling"，以明确本地图所寻找的是什么：规格说明、决定或变更。目的地决定了范围，因此首先确定它。
2. **绘制前沿。** 再次进行拷问，这次是**广度优先**：铺开整个空间，而不是深入任何一条线索，找出悬而未决的决定，以及现在就可以采取的第一步。**如果这一步没有发现迷雾**（通往目的地的路径已经清晰，整个旅程小到一个会话就能装下），你就不需要地图。停下来，问用户希望如何继续。
3. **创建地图**（标签 `wayfinder:map`）：填写目的地和备注，"已做出的决定"留空，并将迷雾勾勒在 **尚未明确的部分** 中。
4. **为你现在能够界定的内容创建工单**，作为地图的子 issue；然后在**第二遍**中连接阻塞边（issue 需要先有 id，才能互相引用）。在这一遍中也要写入交叉引用，并使用真实的 id：占位的 `#<n>` 会自动链接到一个无关的 issue。连线会把它们分拣进前沿或被阻塞的集合；所有你现在还无法界定的内容都留在迷雾中：即 **尚未明确的部分** 一节。
5. **启动研究子智能体。** 对于你刚刚创建的每一张 `research` 工单，启动一个子智能体，调用 Skill 工具并传入 "research"，以并行解决它，并把其发现记录在一次性的 `research/<name>` 分支上，同时从工单中附上上下文指针。推送该分支，但不开 PR：它永远不会被合并。
6. 停止：绘制地图是一个会话的工作，不在此手动解决任何东西。

### 推进地图

用户以一张地图（URL 或编号）来调用。工单是**可选的**：如果没有指定，由你来选择下一个决定，而不是由用户来选。

1. 加载**地图**：看低分辨率的视图，而不是每张工单的正文。
2. 选择工单。如果用户指定了某一张，就用它。否则，取前沿中排在最前的那张工单。**认领它**：在做任何工作之前先把它分配给你自己。
3. 按其 `wayfinder:<type>` 标签所指明的类型来解决它（参见[工单类型](#工单类型)）。要读标签，而不只是正文：正文从不说明类型。**按需放大**：根据需要获取任何相关或已关闭工单的完整正文；调用 Skill 工具，调用 `## 备注` 块中所列出的那些 skill。如果拿不准，就调用两次 Skill 工具，分别传入 "grilling" 和 "domain-modeling"。
4. 记录解决结果：把答案发布为一条**解决评论**，**关闭** issue，并**在地图的已做出的决定中追加一个上下文指针**。
5. 添加新浮现的工单（先创建，再连线）；让答案已能界定的迷雾毕业，并把每一块毕业的补丁从 **尚未明确的部分** 中清除，使其仅存在于其新的工单中。如果答案揭示某张工单（当前这张或另一张）超出了目的地，就将其**划入范围之外**，而不是在路线上去解决它。如果该决定使地图的其他部分失效，就更新或删除那些工单。

用户可能会并行运行那些未被阻塞的工单，因此预计其他会话会同时编辑 tracker。
