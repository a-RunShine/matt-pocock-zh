# 诊断 Bug

针对疑难 bug 的一套纪律。只有在有明确理由的情况下才跳过某个阶段。

探索代码库时，如果存在 `GLOSSARY.md`，请阅读它，以对相关模块形成清晰的心智模型；并检查你所涉及区域的 ADR。

## 脱敏

本 skill 要求你展示命令、输出和捕获的产物。**先对每一个机密进行脱敏**：将其替换为 `<REDACTED>`。通过环境变量构建反馈回路，使凭证留在环境中，而不是出现在你展示的内容里。捕获的产物会携带认证头：只引用携带信号的那几行。

如果脱敏后的输出不足以诊断 bug，就明确说明，并询问用户。

## 第 1 阶段：构建反馈回路

**这才是这个 skill 的核心。** 其余一切都是机械性的。如果你拥有针对此 bug 的**紧凑**通过/失败信号（它会在*这个* bug 上变红），你就能找到根因；二分法、假设检验和插桩，都只是在消耗这个信号。如果没有这样的信号，光盯着代码看也救不了你。

在这一阶段投入远超寻常的精力。**要大胆。要有创意。拒绝放弃。**

### 构建反馈回路的方式，大致按此顺序

1. **失败的测试**，位于能够触达该 bug 的任何接缝处：单元、集成或端到端。
2. **Curl / HTTP 脚本**，针对正在运行的开发服务器。
3. **CLI 调用**，使用固定的输入夹具，将 stdout 与已知良好的快照进行比对。
4. **无头浏览器脚本**（Playwright / Puppeteer），驱动 UI，并对 DOM、控制台或网络进行断言。
5. **重放捕获的追踪**。将一次真实的网络请求/负载/事件日志保存到磁盘；在隔离环境中将其重放通过相应的代码路径。
6. **一次性测试工具（throwaway harness）**。启动系统的一个最小子集（一个服务、模拟的依赖），用一次函数调用来执行该 bug 的代码路径。
7. **属性/模糊测试循环**。如果 bug 是"有时输出错误"，就运行 1000 个随机输入，寻找失败模式。
8. **二分测试工具**。如果 bug 出现在两个已知状态（提交、数据集、版本）之间，就自动化"在状态 X 启动、检查、重复"的过程，以便可以运行 `git bisect run`。
9. **差分循环**。将同一输入分别通过旧版本和新版本（或两套配置）运行，并比对输出。
10. **需要人工参与的 bash 脚本**。最后的手段。如果必须有人点击，就用 `scripts/hitl-loop.template.sh` 来驱动*他们*，使循环仍然保持结构化。捕获的输出会反馈给你。

构建正确的反馈回路，bug 就已经解决了 90%。

### 收紧回路

把回路当作一件产品来对待。一旦有了*一个*回路，就**收紧**它：

- 能否让它更快？（缓存初始化、跳过无关的初始化、缩小测试范围。）
- 能否让信号更锐利？（断言具体的症状，而不是"没有崩溃"。）
- 能否让它更具确定性？（固定时间、为随机数设种子、隔离文件系统、冻结网络。）

一个 30 秒、时好时坏的回路，几乎不比没有回路好；一个 2 秒、确定性的回路，才是紧凑的，是调试的超能力。

### 非确定性 bug

目标不是得到干净的复现，而是得到**更高的复现率**。将触发条件循环 100 次、并行化、增加压力、收窄时序窗口、注入 sleep。一个 50% 概率出现的 flaky bug 是可以调试的；1% 则不行，因此要持续提高复现率，直到它变得可以调试。

### 当你确实无法构建回路时

停下来，并明确说明。列出你尝试过的方法。向用户索取：(a) 能复现该 bug 的环境的访问权限，(b) 脱敏后的捕获产物（HAR 文件、日志转储、核心转储、带时间戳的屏幕录制），或 (c) 添加临时生产环境插桩的许可。在没有回路之前，**不要**进行假设性推测。

### 完成标准：一个紧凑且能变红的回路

当回路是**紧凑**的且**能够变红**时，第 1 阶段即告完成：你能指出**一条命令**（一个脚本路径、一次测试调用、一个 curl），你已经**至少运行过一次**（展示调用方式及其输出，已脱敏），并且它满足：

- [ ] **能够变红**：它驱动的是真正的 bug 代码路径，并断言**用户所遇到的确切症状**，因此它能在该 bug 上变红，并在修复后变绿。不是"运行时没有报错"；它必须能够*捕获这个特定的 bug*。
- [ ] **确定性**：每次运行给出相同的判定（对于 flaky bug：以固定的、较高的复现率来衡量，如上所述）。
- [ ] **快速**：以秒计，而不是以分钟计。
- [ ] **智能体可运行**：你可以无人值守地运行它；人只能通过 `scripts/hitl-loop.template.sh` 参与其中。

如果你发现自己在这条命令存在之前，就已经读代码去构造理论，**停下来：在没有假设之前就直接跳到假设，正是本 skill 要防止的失败。** 没有能变红的命令，就没有第 2 阶段。

## 第 2 阶段：复现与最小化

运行回路。看着它随着 bug 出现而变红。

确认：

- [ ] 回路产生的正是**用户**所描述的失败模式，而不是附近碰巧出现的另一个失败。bug 错了，修复也就错了。
- [ ] 失败在多次运行中可以复现（对于非确定性 bug，以足够高的概率复现，以便调试）。
- [ ] 你已经捕获了确切的症状（错误信息、错误输出、缓慢的时序），以便后续阶段可以验证修复确实解决了它。

### 最小化

一旦变红，就把复现缩减到**仍然能变红的最小场景**。一次删除一项输入、调用方、配置、数据和步骤，每删一项就重新运行回路，只保留对失败起决定作用的部分。

为什么要做这一步：最小的复现会缩小第 3 阶段的假设空间（需要怀疑的活动部件更少），并成为第 5 阶段那个干净的回归测试。

完成标准：**剩下的每个元素都是承重的**：移除其中任何一个，回路就会变绿。

在你既复现又最小化之前，不要继续。

## 第 3 阶段：提出假设

在测试任何一个假设之前，先生成 **3–5 个按优先级排列的假设**。只生成单一假设，会让你锚定在第一个看似合理的想法上。

每个假设都必须**可证伪**：陈述它所做出的预测。

> 格式："如果 <X> 是原因，那么改变 Y 将使 bug 消失 / 改变 Z 将使它变得更糟。"

如果你无法陈述预测，那么这个假设只是一种感觉：丢弃它，或把它磨得更尖锐。

**在测试之前，先把排好序的列表展示给用户。** 他们常常拥有领域知识，能够即时重新排序（"我们刚部署了 #3 相关的变更"），或者知道哪些假设已经被排除。这是一个成本很低、但能节省大量时间的检查点。不要因此阻塞；如果用户离开了，就按你自己的排序继续。

## 第 4 阶段：插桩

每个探针都必须对应第 3 阶段中某个具体的预测。**一次只改变一个变量。**

工具偏好：

1. **调试器 / REPL 检查**，如果环境支持。一个断点胜过十条日志。
2. **有针对性的日志**，放在能够区分各个假设的边界处。
3. 绝不要"把所有东西都打日志，然后 grep"。

**给每条调试日志加上唯一的前缀标记**，例如 `[DEBUG-a4f2]`。清理工作就会变成一次 grep。没有标记的日志会残留下来；有标记的日志会被清除。

**性能分支。** 对于性能回归，日志通常是错误的工具。应当改为：先建立基线测量（计时工具、`performance.now()`、性能分析器、查询计划），然后再进行二分。先测量，再修复。

## 第 5 阶段：修复 + 回归测试

只有当存在一个**正确的接缝**时，才在修复之前编写回归测试。

正确的接缝是指：测试能够在调用点上行使**真实的 bug 模式**。如果唯一可用的接缝过于浅层（只有单一调用者的测试，而 bug 需要多个调用者；或无法复现触发 bug 的调用链的单元测试），那么在那里编写回归测试只会带来虚假的信心。

**如果不存在正确的接缝，这本身就是一项发现。** 记下来。代码库的架构正在阻止这个 bug 被锁定。将其标记给下一阶段。

如果存在正确的接缝：

1. 把最小化后的复现转化为该接缝处的一个失败测试。
2. 看着它失败。如果你是通过修改代码或夹具来强制变红的，就与一份原始副本做 `diff`，证明该修改确实生效了，然后再信任这个结果。
3. 应用修复。
4. 看着它通过。
5. 针对原始的（未最小化的）场景，重新运行第 1 阶段的反馈回路。

## 第 6 阶段：清理

宣告完成之前必须满足：

- [ ] 原始复现不再出现（重新运行第 1 阶段的回路）
- [ ] 回归测试通过（或已记录不存在接缝的情况）
- [ ] 所有 `[DEBUG-...]` 插桩均已移除（对该前缀进行 `grep`）
- [ ] 一次性原型已删除（或移动到明确标记的调试位置）
- [ ] 被证明正确的那个假设已写入提交信息或 PR 信息中，以便下一位调试者能够学到它
