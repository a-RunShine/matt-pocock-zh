# 分诊（Triage）

在项目的 issue tracker 上，通过一套小型的分诊角色状态机来推进 issue。

如果本仓库将外部 pull request 视为一个请求入口（参见 issue tracker 配置），分诊也涵盖它们：**PR 就是附带代码的 issue**，使用相同的角色、相同的状态和相同的机器，但会在下文中以"对于 PR"标注的少数差异处有所不同。将裸的 `#42` 解析为 issue 还是 PR，取决于 tracker 配置。

在分诊过程中发布到 issue tracker 的每一条评论或 issue，**必须**以以下免责声明开头：

```
> *This was generated by AI during triage.*
```

## 参考文档

- [AGENT-BRIEF.md](AGENT-BRIEF.md)：如何撰写持久可用的智能体简报
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)：`.out-of-scope/` 知识库如何运作

## 角色

两个**类别**角色：

- `bug`：某物坏了
- `enhancement`：新功能或改进

五个**状态**角色：

- `needs-triage`：维护者需要评估
- `needs-info`：等待报告者提供更多信息
- `ready-for-agent`：规格已完整，可交给无人值守的智能体
- `ready-for-human`：需要人工实施
- `wontfix`：不会处理

对于 PR，这些状态以附带的代码来解读：`ready-for-agent` 表示已附上简报，应由智能体在 diff 上进行下一步；`ready-for-human` 表示已准备好由人工合并。

每个经过分诊的 issue 都应恰好带有一个类别角色和一个状态角色。如果状态角色之间存在冲突，就标记出来，并在做任何其他事情之前询问维护者。

这些是规范的角色名称。tracker 中实际使用的标签字符串可能不同。映射关系应已提供给你。如果没有，就告诉用户运行 `/setup-matt-pocock-skills`。

状态转换：未打标签的 issue 通常先进入 `needs-triage`；从这里它可以转为 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。报告者回复后，`needs-info` 会回到 `needs-triage`。维护者随时可以覆盖。对看起来异常的转换要加以标记，并在继续之前询问。

## 调用方式

维护者调用 `/triage`，并用自然语言描述他们想要什么。理解请求并付诸行动。示例：

- "给我看看需要我关注的东西"
- "看看 #42"（issue 或 PR）
- "把 #42 移到 ready-for-agent"
- "有哪些已经准备好让智能体来接手？"

## 展示需要关注的内容

查询 issue tracker，并按最早优先的顺序呈现三个分组：

1. **未打标签**：从未经过分诊。
2. **`needs-triage`**：正在评估中。
3. **`needs-info` 且报告者自上次分诊记录以来有过活动**：需要重新评估。

当 PR 在范围之内时，把外部 PR 也纳入这些分组，并在每一行前标注 `[PR]` 或 `[issue]`。发现过程只涵盖*外部* PR（由 tracker 配置定义谁算外部），因此协作者正在进行的 PR 不属于分诊工作。这一过滤仅适用于发现阶段；被明确点名的 PR 无论作者是谁，始终会被分诊。

显示数量和每项一行的摘要。由维护者选择。

## 分诊某个特定 issue 或 PR

1. **收集上下文。** 阅读完整的 issue 或 PR（正文、评论、标签、作者、日期；对于 PR，还包括 diff）。解析已有的分诊记录，避免重复询问已解决的问题。使用项目的领域术语表探索代码库，并尊重该领域的 ADR。对代码库进行两项检查：(a) **冗余性**：按领域概念（而不仅是请求的措辞）搜索是否已有该行为的实现，并报告你搜索过的位置。如果找到，那就是一个已实现的 `wontfix`（见第 5 步）。(b) **先前拒绝**：阅读 `.out-of-scope/*.md`，找出与此请求相似的记录。

2. **给出建议。** 告诉维护者你推荐的类别和状态，并附上理由，以及与该请求相关的简要代码库概述（包括它是否已经实现）。等待指示。

3. **验证主张。** 在任何拷问之前，先检验主张是否成立。对于 bug，按报告者的步骤进行复现。对于 PR，确认 diff 确实做了它声称要做的事：检出代码，运行相关的测试或命令。报告结果：已确认（附代码路径）、失败，或信息不足（这是一个强烈的 `needs-info` 信号）。经过确认的验证会让智能体简报更有分量。

4. **拷问（如有需要）。** 如果请求需要进一步充实，调用两次 Skill 工具，分别传入 "grilling" 和 "domain-modeling"，并以每轮一组问题的方式进行拷问，随着决定落定，就地厘清领域术语，并更新 `GLOSSARY.md`/ADR。

5. **执行结果：**
   - `ready-for-agent`：发布一条智能体简报评论（参见 [AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human`：结构与智能体简报相同，但需说明为何无法委派（需要判断的决定、外部访问、设计决策、人工测试）。
   - `needs-info`：发布分诊记录（模板见下）。
   - 对于 `wontfix`，关闭 issue，评论内容取决于*原因*：
     - **已实现**：该变更已经存在于代码库中。指出它所在的位置；**不要**写入 `.out-of-scope/`（该知识库用于*被拒绝*的请求，而非已经构建好的功能）。
     - **被拒绝（bug）**：给出礼貌的解释，然后关闭。
     - **被拒绝（enhancement）**：写入 `.out-of-scope/`，在评论中链接到它，然后关闭（参见 [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage`：应用该角色。如果有部分进展，可选择添加评论。

## 快速状态覆盖

如果维护者说"把 #42 移到 ready-for-agent"，就信任他们，直接应用该角色。在执行之前确认你将要做的事（角色变更、评论、关闭），然后再行动。跳过拷问。如果是在没有经过拷问的情况下移到 `ready-for-agent`，就询问他们是否想撰写一份智能体简报。

## 需要信息的模板

```markdown
## 分诊记录

**目前已确认的内容：**

- 要点 1
- 要点 2

**我们仍需要你（@报告者）提供的信息：**

- 问题 1
- 问题 2
```

把拷问期间已解决的所有内容都记录在"目前已确认的内容"之下，以免工作成果丢失。问题必须具体且可操作，而不是"请提供更多信息"。

## 恢复之前的会话

如果 issue 或 PR 上已有先前的分诊记录，就阅读它们，检查报告者是否已回答任何悬而未决的问题，并在继续之前呈现更新后的全貌。不要重复询问已解决的问题。
