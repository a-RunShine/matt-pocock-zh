# 范围之外知识库

仓库中的 `.out-of-scope/` 目录保存被拒绝的功能请求的持久记录。它有两个用途：

1. **机构记忆**：记录功能被拒绝的原因，使理由不会随着 issue 关闭而丢失
2. **去重**：当一个新 issue 与先前的拒绝相匹配时，skill 可以呈现之前的决定，而不是重新争论

## 目录结构

```
.out-of-scope/
├── dark-mode.md
├── plugin-system.md
└── graphql-api.md
```

每个**概念**一个文件，而不是每个 issue 一个文件。请求同一件事的多个 issue 会归入同一个文件。

## 文件格式

文件应以宽松、易读的风格撰写，更像一份简短的设计文档，而不是数据库条目。使用段落、代码示例和实例，使推理清晰，并对第一次遇到它的人有用。

```markdown
# 深色模式

本项目不支持深色模式或面向用户的主题定制。

## 为什么超出范围

渲染管线假定使用 `ThemeConfig` 中定义的单一调色板。支持多个主题需要：

- 一个包裹整个组件树的主题上下文提供者
- 每个组件的、感知主题的样式解析
- 用于保存用户主题偏好的持久化层

这是一项重大的架构变更，与本项目专注于内容创作的方向不符。主题定制是下游使用者（即嵌入或再分发输出的人）所关心的问题。

```ts
// 当前的 ThemeConfig 接口并非为运行时切换而设计：
interface ThemeConfig {
  colors: ColorPalette; // 单一调色板，在构建时解析
  fonts: FontStack;
}
```

## 先前的请求

- #42："添加深色模式支持"
- #87："为无障碍使用的夜间主题"
- #134："深色主题选项"
```

### 命名文件

为概念使用简短、描述性的 kebab-case 名称：`dark-mode.md`、`plugin-system.md`、`graphql-api.md`。名称应当足够可辨识，使浏览目录的人无需打开文件，就能理解被拒绝的是什么。

### 撰写理由

理由应当实质性：不是"我们不想要这个"，而是为什么。好的理由会引用：

- 项目范围或理念（"本项目专注于 X；主题定制是下游的关切"）
- 技术约束（"支持这一点需要 Y，这与我们的 Z 架构相冲突"）
- 战略决策（"我们选择 A 而非 B，是因为……"）

理由应当持久。避免引用暂时性的情况（"我们现在太忙了"）；那些不是真正的拒绝，只是推迟。

## 何时检查 `.out-of-scope/`

在分诊期间（第 1 步：收集上下文），读取 `.out-of-scope/` 中的所有文件。评估一个新 issue 时：

- 检查该请求是否与某个现有的范围之外概念相匹配
- 匹配依据是概念相似性，而不是关键词："夜间主题"与 `dark-mode.md` 相匹配
- 如果有匹配，就向维护者呈现："这与 `.out-of-scope/dark-mode.md` 相似。我们之前拒绝它是因为[理由]。你仍然持相同看法吗？"

维护者可以：

- **确认**：新 issue 被添加到现有文件的"先前的请求"列表中，然后关闭
- **重新考虑**：范围之外的文件被删除或更新，该 issue 按正常分诊流程继续
- **不同意**：这些 issue 相关但不同，按正常分诊流程继续

## 何时写入 `.out-of-scope/`

仅当一个**功能增强**（而非 bug）被以 `wontfix` 拒绝时。这同样适用于增强类 PR，与 issue 完全一样：被拒绝的 PR 也记录在此，使同样的请求不会以新代码的形式再次出现。

当某件事因为**已经实现**而以 `wontfix` 关闭时，**不要**写在这里。那是一个已构建的功能，而不是被拒绝的功能；记录它会用虚假的拒绝污染去重检查。相应地，关闭评论应指向该功能已经存在的位置。

流程：

1. 维护者判定某个功能请求超出范围
2. 检查是否已存在匹配的 `.out-of-scope/` 文件
3. 如果存在：将新 issue 追加到"先前的请求"列表
4. 如果不存在：以概念名称、决定、理由以及第一个先前请求新建一个文件
5. 在 issue 上发布评论，解释该决定并提及 `.out-of-scope/` 文件
6. 以 `wontfix` 标签关闭 issue

## 更新或删除范围之外的文件

如果维护者改变了对先前被拒绝概念的看法：

- 删除 `.out-of-scope/` 中的文件
- skill 无需重新打开旧 issue；它们是历史记录
- 触发重新考虑的新 issue 按正常分诊流程继续
