# 撰写智能体简报

智能体简报是在 issue 或 PR 转为 `ready-for-agent` 时，发布在 GitHub issue 或 PR 上的一条结构化评论。它是无人值守智能体将要遵循的权威规格。原始正文和讨论是背景；智能体简报才是契约。

简报说明**智能体应当做什么**，它延伸到两种载体：对于 issue，是从零开始构建变更；对于 PR，则是针对*现有 diff* 还剩下什么要做：完成它、补上缺口、回应评审意见。两者的原则相同；下面的 PR 示例展示了区别。

## 原则

### 持久性优先于精确性

issue 可能在 `ready-for-agent` 状态中停留数天或数周。在此期间代码库会发生变化。撰写简报时，应使其即使在文件被重命名、移动或重构之后依然有用。

- **应当**描述接口、类型和行为契约
- **应当**指明智能体应当查找或修改的具体类型、函数签名或配置结构
- **不要**引用文件路径：它们会过时
- **不要**引用行号
- **不要**假设当前的实现结构会保持不变

### 行为性，而非程序性

描述系统**应当做什么**，而不是**如何**实现。智能体会重新探索代码库，并自行做出实现决定。

- **好：**"`SkillConfig` 类型应接受一个类型为 `CronExpression` 的可选 `schedule` 字段"
- **坏：**"打开 src/types/skill.ts，并在第 42 行添加一个 schedule 字段"
- **好：**"当用户不带参数运行 `/triage` 时，他们应当看到需要关注的 issue 摘要"
- **坏：**"在主处理函数中添加一个 switch 语句"

### 完整的验收标准

智能体需要知道何时算完成。每份智能体简报都必须有具体、可测试的验收标准。每条标准都应可以独立验证。

- **好：**"运行 `gh issue list --label needs-triage` 返回的 issue 都已经过初步分类"
- **坏：**"分诊应当正常工作"

### 明确的范围边界

说明什么是超出范围的。这可以防止智能体过度打磨，或对相邻功能做出假设。

## 模板

```markdown
## 智能体简报

**类别：** bug / enhancement
**摘要：** 对需要发生之事的一行描述

**当前行为：**
描述现在发生的情况。对于 bug，这是出错的行为。
对于增强，这是该功能所依托的现状。

**期望行为：**
描述智能体工作完成后应当发生的情况。
对边缘情况和错误条件要具体。

**关键接口：**
- `TypeName`：需要改变什么，以及为什么
- `functionName()` 的返回类型：它现在返回什么，应当返回什么
- 配置结构：需要的任何新配置选项

**验收标准：**
- [ ] 具体、可测试的标准 1
- [ ] 具体、可测试的标准 2
- [ ] 具体、可测试的标准 3

**范围之外：**
- 不应在本 issue 中改动或处理的事项
- 看似相关但实际独立的相邻功能
```

## 示例

### 好的智能体简报（bug）

```markdown
## 智能体简报

**类别：** bug
**摘要：** Skill 描述截断时会在词中间切断，产生错误的输出

**当前行为：**
当 skill 描述超过 1024 个字符时，它会恰好在第 1024 个字符处截断，无论词的边界在哪里。
这会产生在词中间结束的描述（例如 "Use when the user wants to confi"）。

**期望行为：**
截断应在 1024 个字符之前的最后一个词边界处进行，并追加 "..." 以表示被截断。

**关键接口：**
- `SkillMetadata` 类型的 `description` 字段：不需要改变类型，
  但填充它的验证/处理逻辑需要尊重词边界
- 任何读取 SKILL.md frontmatter 并提取描述的函数

**验收标准：**
- [ ] 少于 1024 个字符的描述保持不变
- [ ] 超过 1024 个字符的描述在 1024 个字符之前的最后一个词边界处截断
- [ ] 被截断的描述以 "..." 结尾
- [ ] 包括 "..." 在内的总长度不超过 1024 个字符

**范围之外：**
- 修改 1024 字符的限制本身
- 多行描述支持
```

### 好的智能体简报（enhancement）

```markdown
## 智能体简报

**类别：** enhancement
**摘要：** 添加 `.out-of-scope/` 目录支持，用于跟踪被拒绝的功能请求

**当前行为：**
当一个功能请求被拒绝时，该 issue 会以 `wontfix` 标签和一条评论关闭。
没有关于该决定及其理由的持久记录。
之后类似的请求需要维护者回忆或搜索先前的讨论。

**期望行为：**
被拒绝的功能请求应记录在 `.out-of-scope/<concept>.md` 文件中，
这些文件记录决定、理由，以及所有请求该功能的 issue 链接。
分诊新 issue 时，应检查这些文件是否有匹配项。

**关键接口：**
- `.out-of-scope/` 中的 Markdown 文件格式：每个文件应有
  `# 概念名称` 标题、一行 `**Decision:**`、一行 `**Reason:**`，
  以及一个带 issue 链接的 `**Prior requests:**` 列表
- 分诊工作流应尽早读取所有 `.out-of-scope/*.md` 文件，
  并按概念相似性将新 issue 与之匹配

**验收标准：**
- [ ] 将功能以 wontfix 关闭时，会在 `.out-of-scope/` 中创建或更新文件
- [ ] 文件包含决定、理由，以及指向已关闭 issue 的链接
- [ ] 如果已存在匹配的 `.out-of-scope/` 文件，新 issue 会被追加到
      其"先前的请求"列表中，而不是创建重复文件
- [ ] 分诊期间，当新 issue 与先前的拒绝相匹配时，
      会检查并呈现现有的 `.out-of-scope/` 文件

**范围之外：**
- 自动匹配（由人工确认匹配）
- 重新打开先前被拒绝的功能
- bug 报告（只有增强被拒绝才进入 `.out-of-scope/`）
```

### 好的智能体简报（PR）

对于 PR，"当前行为"描述的是 diff 的状态，简报要求智能体完成或修复它，而不是从零开始构建。

```markdown
## 智能体简报

**类别：** enhancement
**摘要：** 完成贡献者为 `triage list` 添加的 `--json` 输出标志

**当前行为：**
该 PR 添加了一个 `--json` 标志，可将 issue 列表序列化为 JSON。正常路径可以工作，
diff 也与项目的命令结构相符。仍有两处缺口：错误仍以人类可读的文本输出
（而非 JSON），并且新标志没有测试覆盖。

**期望行为：**
使用 `--json` 时，所有输出（包括错误）都是格式良好的 JSON，输出到 stdout，
且命令的退出码保持不变。不带该标志时，现有的人类可读输出完全不变。

**关键接口：**
- 命令的错误路径在 `--json` 下应输出 `{ "error": string }`，
  而不是纯文本错误
- 复用 PR 已经添加的现有序列化器；不要引入第二个

**验收标准：**
- [ ] `triage list --json` 在成功和错误两种情况下都输出有效的 JSON
- [ ] 退出码与非 JSON 命令一致
- [ ] 有一个测试覆盖 `--json` 的成功输出和一个错误情况
- [ ] 默认（非 JSON）输出逐字节不变

**范围之外：**
- 为任何其他命令添加 `--json`
- 改变 PR 已经定义的成功负载的 JSON 结构
```

### 糟糕的智能体简报

```markdown
## 智能体简报

**摘要：** 修复分诊 bug

**要做什么：**
分诊那部分坏了。看看主文件，修复它。
第 150 行附近的函数有问题。

**需要修改的文件：**
- src/triage/handler.ts（第 150 行）
- src/types.ts（第 42 行）
```

这份简报的问题在于：
- 没有类别
- 描述含糊（"分诊那部分坏了"）
- 引用了会过时的文件路径和行号
- 没有验收标准
- 没有范围边界
- 没有描述当前行为与期望行为的对比
