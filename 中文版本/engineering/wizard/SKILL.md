# 向导（Wizard）

**向导**是一个 bash 脚本，它会逐步带领人类完成一个手工流程：这个流程手动做起来很繁琐，而且每次都要向 AI 重新解释一遍同样繁琐。它会打开每个 URL，明确告诉用户要点击什么、复制什么，捕获取得的值，把它们写入应当存放的位置（`.env`、GitHub secrets），在每个阶段进行确认，并显示还剩多少个阶段。它可能用于配置第三方服务、执行一次性迁移，或把项目从一种状态转换到另一种状态。

[template.sh](template.sh) 已经解决了这套出色的用户体验：逐阶段的进度显示、确认关卡、跨平台的 URL 打开（包括 WSL）、隐藏的密钥输入、幂等的 `.env` 写入（upsert）、`gh secret` / `gh variable` 写入，以及结束时的总结。**你的工作仅限于界定流程范围，并编写它的各个阶段。** `STAGES` 标记之上的库在每个向导中都完全相同；这种一致性正是它的意义所在：永远不要手动编辑它。

向导默认是临时的：为某一次运行而建，保存在临时目录或 `scripts/` 路径下，任务完成后删除。只有当用户希望有一条可重复使用、应当存在于仓库中的设置路径时，才将其提交。

## 流程

### 1. 界定流程范围

找出人类必须执行的每一个手工步骤，以及沿途需要捕获的每一个值。先读仓库，不要冷启动提问：

- 对于环境设置：`.env`、`.env.example`、`.env.*`、`README`、`docker-compose*`、框架配置，以及 `.github/workflows/*`（每一个 `secrets.*` / `vars.*` 引用都是向导必须产出的一个值）。
- 对于迁移或过渡：当前状态、目标状态，以及两者之间不可逆的动作。

然后向用户展示有序的阶段列表，以及每个阶段产出的值，并请用户确认：他们可以增加、删除或重新排序。

**完成标准：** 每个阶段都已按顺序命名；对于每个捕获的值，你都知道 (a) 人类从哪里获取它，(b) 它被写到哪里（`.env`、GitHub secret、两者都写，或者不写；有些阶段纯粹是动作），以及 (c) 它是机密（隐藏输入）还是公开值。

### 2. 映射每个阶段的操作路径

对每个阶段，写出人类应遵循的精确路径：打开哪个 URL，在那里做什么，值显示在哪里，填入哪个变量。例如："Dashboard → Developers → API keys → Reveal test key → copy"。如果你并不确定当前的界面或确切命令，就直说出来，并询问用户或查阅文档：绝不凭空编造可能并不存在的步骤。

**完成标准：** 每个阶段都能追溯到一个陌生人也能照着做的具体指令。

### 3. 编写向导

把 `template.sh` 复制到目标路径。将示例阶段替换为每个步骤对应的一个 `stage`，并按依赖顺序排列。使用库中的辅助函数：`stage`、`say`/`step`、`open_url`、`ask`/`ask_secret`、`write_env`、`set_secret`/`set_var`、`pause`/`confirm`。把 `TOTAL_STAGES` 设为你编写的阶段数。

遵守模板设定的标准：在询问某个值之前先打开它的 URL；对任何机密使用 `ask_secret`；每个需要持久化的值都要通过 `write_env` 写入；`set_secret` 只用于 CI 真正需要的值；在任何不可逆操作之前使用 `confirm`。每个 `stage` 都会清屏，使得只有当前步骤可见：让每个阶段只包含一个专注的任务，保证人类需要的内容不会滚动消失。不要改动标记之上的库。

### 4. 验证并交接

- 运行 `bash -n <script>`；若可用，再运行 `shellcheck`。
- 执行 `chmod +x <script>`。
- 不要自己端到端运行它：它会打开浏览器，并阻塞等待人工输入。改为进行静态追踪：确认步骤 1 中的每个值都被捕获，并写入步骤 1 所说的位置；每个 `set_secret` 的名称都与 CI 中的某个 `secrets.*` 引用完全一致。
- 告诉用户如何运行它。如果它是一条可重复使用的设置路径，就把它提交，并从 README 链接过去，让下一个人运行脚本，而不是再去问 AI。
