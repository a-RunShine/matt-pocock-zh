# 改进代码库架构

发现架构摩擦，并提出**深化机会**：即把浅层模块改造为深层模块的重构。目标是可测试性和 AI 可导航性。

本命令以项目的领域模型为依据，并建立在一套共享的设计词汇之上：

- 调用 Skill 工具并传入 "codebase-design"，获取架构词汇（**模块（module）**、**接口（interface）**、**深度（depth）**、**接缝（seam）**、**适配器（adapter）**、**杠杆（leverage）**、**局部性（locality）**）及其原则（删除测试、"接口即测试表面"、"一个适配器 = 假设性接缝，两个 = 真实接缝"）。每条建议都要准确使用这些术语，不要滑向"组件"、"服务"、"API"或"边界"。
- `GLOSSARY.md` 中的领域语言为好的接缝命名；`docs/adr/` 中的 ADR 记录了本命令不应重新讨论的决定。

## 流程

### 1. 探索

**先确定范围再扫描：YAGNI。** 深化一个模块的回报在于让未来对它的修改更容易，因此应更重视近期发生过变化的部分代码。在查看之前，先决定_往哪里看_：

- 如果用户指定了某个方向（某个模块、某个子系统、某个痛点），就采纳它，并跳过下面的推断。
- 否则，回溯一段相当长的提交历史（`git log --oneline`），找出代码库的热点：反复出现的文件和区域，让这些路径优先吸引你的注意。如果变更分散、没有明显的热点，就扩大搜索范围。

先阅读项目的领域术语表（`GLOSSARY.md`）以及你所涉及区域的 ADR。

然后启动一个子智能体来遍历代码库。不要套用僵硬的启发式规则，而是有机地探索，并记录你在哪里感受到摩擦：

- 理解一个概念时，是否需要在许多小模块之间来回跳转？
- 哪些模块是**浅层的**，即接口几乎与实现一样复杂？
- 是否有纯函数只是为了可测试性而被抽取出来，但真正的 bug 却隐藏在它们被调用的方式中（缺乏**局部性**）？
- 紧密耦合的模块是否在其接缝处发生泄漏？
- 哪些部分未经测试，或者很难通过其当前接口进行测试？

对你怀疑是浅层的任何东西应用**删除测试**：如果删除它，复杂性会集中起来，还是只会转移？"是的，会集中起来"正是你想要的信号。

### 2. 以 HTML 报告呈现候选项

将一个自包含的 HTML 文件写入操作系统的临时目录，这样不会有任何文件落入仓库。从 `$TMPDIR` 解析临时目录，若未设置则回退到 `/tmp`（Windows 上为 `%TEMP%`），并写入 `<tmpdir>/architecture-review-<timestamp>.html`，使每次运行都生成一个新文件。为用户打开它（Linux 上用 `xdg-open <path>`，macOS 上用 `open <path>`，Windows 上用 `start <path>`），并告诉用户其绝对路径。

报告使用 **Tailwind（通过 CDN）** 进行布局和样式设计，并在图和结构关系较为清晰时使用 **Mermaid（通过 CDN）** 绘制图表。将 Mermaid 与手工绘制的 CSS/SVG 视觉效果结合使用：当关系呈图状（调用图、依赖关系、时序）时使用 Mermaid；当你希望呈现更具编辑风格的效果（质量分布图、剖面图、折叠动画）时，使用手工制作的 div/SVG。每个候选项都要有**前后对比的可视化**。要具有视觉性。

对于每个候选项，渲染一张卡片，包含：

- **文件**：涉及哪些文件/模块
- **问题**：为什么当前架构会造成摩擦
- **解决方案**：用平实的语言描述将要发生的变化
- **收益**：从局部性和杠杆的角度解释，以及测试将如何改善
- **前后对比图**：并排展示，手工绘制，说明浅层性以及深化后的样子
- **推荐强度**：`Strong`（强）、`Worth exploring`（值得探索）、`Speculative`（推测性）之一，以徽章形式呈现

报告结尾是一个**首要推荐**部分：说明你会首先处理哪个候选项，以及原因。

**领域用 GLOSSARY.md 的词汇，架构用 `/codebase-design` 的词汇。** 如果 `GLOSSARY.md` 定义了"Order"，就说"Order 接收模块"，而不是"FooBarHandler"，也不是"Order 服务"。

**ADR 冲突**：如果某个候选项与现有 ADR 相矛盾，只有当摩擦真实到足以值得重新审视该 ADR 时才提出。在卡片中清楚标注（例如用警告提示框：_"与 ADR-0007 相矛盾，但值得重新审视，因为……"_）。不要列出 ADR 禁止的每一种理论上的重构。

完整的 HTML 脚手架、图示模式和样式指南参见 [HTML-REPORT.md](HTML-REPORT.md)。

不要在此阶段提出接口方案。文件写好之后，询问用户："你想探索其中哪一个？"

### 3. 拷问循环

用户选定某个候选项后，调用 Skill 工具并传入 "grilling"，与其一同梳理决策树：约束、依赖、深化后模块的形态、接缝后面是什么，以及哪些测试会保留下来。

随着决定逐步明确，就地产生副作用；调用 Skill 工具并传入 "domain-modeling"，在推进过程中保持领域模型的更新：

- **如果深化后的模块以一个不在 `GLOSSARY.md` 中的概念来命名？** 将该术语添加到 `GLOSSARY.md`。如果文件尚不存在，则延迟创建。
- **在对话中锐化了某个模糊术语？** 立即更新 `GLOSSARY.md`。
- **用户以一个有分量的理由拒绝了某个候选项？** 提议将其记录为 ADR，措辞为：_"要我把它记录成 ADR，让将来的架构评审不再重复提出它吗？"_ 只有当某个理由确实需要被未来的探索者知道，以免再次提出同样的建议时，才提出；跳过临时性的理由（"现在不值得做"）和不言自明的理由。
- **想探索深化模块的其他接口方案？** 调用 Skill 工具并传入 "codebase-design"，使用其"设计两次"（design-it-twice）的并行子智能体模式。
