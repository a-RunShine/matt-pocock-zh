# 问问 Matt

你记不住每一个 skill，那就问一下。

在说明某个 skill 做什么，或建议跳过某个步骤之前，先阅读该 skill 的 SKILL.md：这里的概述只用于大致定位。

**流程（flow）**是穿过这些 skill 的一条路径。大多数路径沿着一条**主流程**前进，另有两个**入口匝道（on-ramp）**汇入主流程。其余的要么是独立的，要么是在底层运行的词汇层。

## 主流程：想法 → 交付

大多数工作所走的路线。你有一个想法，并希望把它做出来。

1. **`/grill-with-docs`** 通过访谈来打磨想法。只要你**在某个工作目录中工作**，就从这里开始：它是有状态的，会把所学到的内容保留在 `GLOSSARY.md` 和 ADR 中。（没有工作目录？请改用 `/grill-me`，见"独立"一节。两者运行的是同一个 `/grilling` 原语；`grill-with-docs` 会留下书面记录，因此只要有仓库可以留下记录，它就是更好的选择。）
2. **分支：能否在对话中解决每一个问题？** 如果某个问题需要可运行的答案（状态、业务逻辑、需要亲眼看到的 UI），就绕道进入原型，并通过双向的 **`/handoff`** 衔接（原型位于自己的目录中，这正是 `/handoff` 的用途；参见"阶段边界"）：
   - 用 **`/handoff`** 导出，然后打开一个针对该文件的新会话，
   - 用 **`/prototype`** 以一次性代码回答问题，
   - 用 **`/handoff`** 把所学内容带回来，并从原始想法的线程中引用它。
3. **分支：这是一个跨多个会话的构建吗？**
   - **是** → 用 **`/to-spec`**（把线程转化为规格说明），然后用 **`/to-tickets`** 把它拆分为示踪弹式的工单，每张工单声明其**阻塞边**。然后有两种方式处理工单：
     - 每张工单用一次 **`/implement`**，**每张之间 `/clear` 上下文**。在本地 tracker 上，这是 `.scratch/<feature>/issues/` 下每张工单一个文件，由人工按阻塞者优先的顺序处理；在真实 tracker 上，这些边会变成原生的阻塞链接，因此任何阻塞项都已完成的工单都可以被领取。每张工单都是自包含的，因此上一张的上下文可以丢弃。
     - 用 **`/implement-spec`** 在一次运行中完成整份规格。它把工单当作**任务图**读取，在就绪的**前沿**上并行运行实现者子智能体，并把所有结果落到一条**集成分支**上。当你更愿意让它编排构建、而不是亲自驱动每张工单时，就用它。
   - **否** → 就在这里，在同一个上下文窗口中直接执行 **`/implement`**。

   无论哪种方式，代码都是通过驱动 **`/tdd`**（一次一个红-绿切片）来构建的，并以 **`/code-review`** 收尾，即对 diff 进行双维度（规范 + 规格）评审。`/implement` 对每张工单各运行一次这两者；`/implement-spec` 的每个实现者各自驱动 `/tdd`，并在集成分支上运行一次 `/code-review`。若只想以测试先行的方式构建某个具体行为、而不需要完整规格，就单独使用 **`/tdd`**；若想针对某个固定基准点评审分支或 PR，就单独使用 **`/code-review`**。

   当工作以 Pull Request 的形式提交时，用 **`/pr`** 撰写 PR 正文：用最小的可视化形式展示变更，给出它有效的前后证据，并判断它是单向门还是双向门。它是模型调用型的，因此智能体在撰写 PR 时会主动使用它。

4. **`/retro`** 收尾这个循环。一次构建完成之后，尤其是出了岔子的构建，它会回顾会话，并建议对智能体**环境**（而非代码）做出改进：导航指针、自动化检查、`/code-review` 所执行的编码规范、引导文件、工具。机械性的错误变成确定性的检查；判断性的问题变成编码规范。下一次构建就从更好的环境开始。

### 上下文卫生

步骤 1–3 要保持在**一个不间断的上下文窗口**中（在 `/to-tickets` 完成之前不要压缩或清除），使拷问、规格说明和工单都建立在同一思路之上。之后每个 `/implement` 都从全新开始，以工单为依据工作。在清除之前，在要回顾的那个会话中运行 `/retro`；清除之后，则让它指向该会话的日志。

限制在于 **[smart zone（智能区）](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**：即窗口（最先进的模型约为 150k token）之内，模型仍能敏锐地推理。如果会话在 `/to-tickets` 之前接近该上限，不要在退化状态下硬撑；在最近的阶段边界处执行 `/compact`，然后继续（参见"阶段边界"）。

## 入口匝道

一种会产生工作的起始情境，随后汇入主流程。

- **bug 和请求堆积** → **`/triage`**。它把 issue 推进经过分诊角色，并产出可供智能体执行的 issue，之后由 **`/implement`** 拾取。

  分诊只针对你**没有创建**的 issue：bug 报告、收到的功能请求，以及任何未经加工而到达的东西。`/to-tickets` 产出的工单已经可以交给智能体，因此**不要对它们进行分诊**。

- **出了故障** → **`/diagnosing-bugs`**。用于那些难啃的硬骨头：乍看之下难以解决的 bug、间歇性的 flake，或在两个已知良好状态之间悄然出现的回归。它拒绝在没有**短促而稳定的反馈回路**（一条已经能在_这个_ bug 上变红的命令）之前进行推测，然后通过回归测试来修复。修复完成后，在同一个会话中运行 **`/retro`**，询问什么本可以防止这个 bug；如果真正的发现是没有好的接缝可以锁定它，那就交给 **`/improve-codebase-architecture`**。

- **庞大而模糊的工作：绿地项目或超出单个会话的大型功能构建** → **`/wayfinder`**。这是这里认知要求最高的流程。当从这里到目的地的路径还看不见时，它会在 issue tracker 上绘制一张**决策工单**的**共享地图**，并逐一解决它们，产出的是**决定，而不是交付物**，直到迷雾被推开、路线清晰为止。**`/grill-with-docs`** 用于锐化一个能在单个会话中装下的想法，而 wayfinder 用于那些装不下的想法；它更慢、更密集，因此应留给恰好需要它的情形，绝不要用在范围明确的功能上。

  当地图清晰后，它**交接而不是构建**：并入主流程的 **`/to-spec`**，由它把地图中相互关联的决定汇总为一份可构建的计划，然后再进行 `/to-tickets` 和 `/implement`。只有当工作结果确实很小时，才直接跳到 `/implement`；否则，把地图直接接到 `/implement` 会丢弃那些被关联的细节。

## 代码库健康

不属于功能开发，只是日常维护。

- **`/improve-codebase-architecture`** 在你有闲暇时运行，用以保持代码库适合智能体运作。它会发现**深化机会**；选中其中一项，就会_产生一个想法_，你可以将其带入主流程的 `/grill-with-docs`。它是发现候选项的勘测工具；而 **`/codebase-design`**（见下文）是你用来设计所选方案的工作台。

## 底层的词汇

两个模型调用型的参考，运行在其他 skill _之下_，各自是其词汇的唯一事实来源。当问题出在**词语**而非**流程**上时，直接使用它们；或者让上面的 skill 去拉取它们。

- **`/domain-modeling`**：打磨项目的*领域*语言：质疑一个模糊的术语，消解一个被过度使用的词（例如"account"同时承担三种含义），把难以逆转的决定记录为 ADR。它是 `/grill-with-docs` 所驱动的主动纪律，用以让 `GLOSSARY.md` 保持为一份干净的术语表。
- **`/codebase-design`**：深层模块的词汇（模块、接口、深度、接缝、适配器、杠杆、局部性），用于设计模块的_形态_：在一个干净的接缝处，于一个小接口背后放置大量行为。`/tdd` 和 `/improve-codebase-architecture` 都使用这套语言。

## 阶段边界

**阶段（phase）**是会话中的一块工作：拷问、实现、QA。在两个阶段的**边界**处，你有五种选择，而在它们之间做选择，是整张地图中最模糊的决定：

- **继续（Continue）**：留在原处。不花费任何代价，也不丢失任何东西。
- **`/clear`**：清空窗口，适用于此处的任何内容都与接下来的工作无关时。
- **`/handoff`** 会写出一个可移植的 markdown 文件。范围很窄：仅用于**新的 harness**、**新的目录**、**同事**，或在**阶段中途**分叉出一个旁支任务。它换来的是可移植性。
- **子智能体（Subagent）**：把一个范围严格的任务发送到它自己的窗口，并取回一份报告。
- **`/compact`** 压缩当前上下文，并用它为一个新会话提供种子。这是**默认选项**，位于决策树的底部，而不是首先考虑的选择。

阅读 [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md) 可以了解有序的决策树：五个问题、每个分支背后的理由，以及为什么一手来源的成本使**继续**成为应当首先排除的选项。在边界处做出决定；在阶段中途，则继续或把剩余工作拆分给子智能体。

## 独立

完全脱离主流程。

- **`/grill-me`**：与 `/grill-with-docs` 相同的无情访谈，但它是**无状态的**：不在本地保存任何内容，也不构建 `GLOSSARY.md`。当你**不在某个工作目录中**时使用它（打磨计划、设计、一篇文章，或任何没有仓库作为底座的东西）。如果你在工作目录中，请改用 `/grill-with-docs`：它进行同样的访谈，并留下书面记录，因此严格来说是更好的选择。
- **`/grilling`** 是访谈的原语本身：轮次、前沿、事实由智能体负责查找，决定由你做出。`/grill-me` 和 `/grill-with-docs` 是两种有名字的入口；`/triage`、`/wayfinder` 和 `/improve-codebase-architecture` 都在内部运行它。只有当你想要访谈本身、而不需要任何外层包装时，才直接使用它。
- **`/prototype`** 是一个小型的一次性程序，用来回答一个设计问题：这个状态模型感觉对不对，或者这个 UI 应该长什么样。"一次性"是对代码编写方式的约束，而不是销毁它的承诺：答案会并入真正的代码，而原型本身会作为**一手来源**保存在从 main 分出的 `prototype/<name>` 分支上，并从实现 issue 中指向它。它是主流程第 2 步中的绕道，但凡一个设计问题在纸面上难以定夺时，都可以使用它。
- **`/research`**：把阅读类的劳动委派给**后台智能体**：它依据**一手来源**调查一个问题，然后在仓库中留下一份带引用的 Markdown 文件。你可以在它阅读时继续工作。它产出的文件是需要带入主流程 `/grill-with-docs` 的材料，因为研究是为思考提供养分，而不是取代思考。
- **`/to-questionnaire`** 在阻碍你的东西不在你的脑子里或代码库中，而是在**别人的脑子里**时出场，并为他们撰写一份供填写的问卷。它与 `/grill-me` 相反：它不访谈你关于主题，而是访谈你关于**发送**（发给谁，以及需要回传什么），并把问题对准缺口。收回的内容是 `/grill-with-docs` 或 `/to-spec` 的材料。
- **`/wizard`** 用于那些只有**人类**才能完成的步骤：配置基础设施、设置凭证或 CI 密钥、点击一个不熟悉的第三方控制台、执行一次性迁移或切换。它会生成一个交互式 bash 脚本，逐一打开各个 URL，捕获每个值，并将其写入 `.env` 和 GitHub secrets，从而让这一流程不再需要每次都向智能体重新解释。它是模型调用型的，因此智能体在撞上只有你能通过的墙时会立即使用它。如果智能体自己就能完成，它就应该自己做；这个 skill 只适用于确实需要人类在回路中的情形。
- **`/wait-what`** 用于纠正一条没有被理解的消息。在任何其他 skill 的会话中途使用它，智能体会用你所缺失的背景、以平白的英语、使用 `GLOSSARY.md` 的词汇，重新表述它刚才说的内容。它是事后补救；`/grill-with-docs` 才是事前的根治，因为尽早达成一致的共享语言，才能阻止行话出现在一开始。
- **`/teach`**：在多次会话中学习一个概念，将当前目录用作有状态的工作区。
- **`/writing-for-agents`** 是为撰写供智能体消费的文档（skill、AGENTS.md、被指向的文档）提供的参考。

## 前提条件

**`/setup-matt-pocock-skills`**：在你第一次使用任何工程流程之前运行，用以配置其他 skill 所假定的 issue tracker、分诊标签和文档布局。自定义的 issue tracker 同样适用。
