# UI 原型

在单个路由上生成**几种截然不同的 UI 变体**，可通过浮动的底部栏切换。用户在浏览器中在各个变体之间翻看，选定一个（或从每个中各取所长），然后丢弃其余的。

如果问题关乎逻辑或状态，而不是某物看起来怎样，那就选错了分支。请改用 [LOGIC.md](LOGIC.md)。

## 何时适用这种形式

- "这个页面应该长什么样？"
- "在敲定之前，我想看看这个仪表盘的几种方案。"
- "设置页换一种布局试试。"
- 任何时候，用户原本会在脑子里对三个含糊的草图纠结一整天。

## 两种子形式：强烈优先子形式 A

当 UI 原型**紧贴应用的其余部分**时，要评判它容易得多：真实的头部、真实的侧边栏、真实的数据、真实的信息密度。单独一个一次性路由就是真空：每个变体单独看都没问题。只要存在一个看似合理、可以承载这些变体的现有页面，就默认使用子形式 A。只有当原型确实没有附近的归属位置时，才使用子形式 B。

### 子形式 A：对现有页面的调整（优先）

该路由已经存在。变体在**同一路由**上渲染，由 `?variant=` URL 查询参数控制。现有的数据获取、参数和鉴权全部保留。只替换渲染部分。这是默认选择；除非有具体理由不选它，否则就用它。

如果原型针对的是一个尚无页面、但_自然应当位于某个页面之内_的东西（仪表盘的一个新板块、设置屏的一张新卡片、现有流程中的一个新步骤），它仍然属于子形式 A。把变体挂载到宿主页面之内。

### 子形式 B：新页面（最后手段）

只有当被原型化的东西确实没有可以容纳它的现有页面时才使用（例如一个全新的顶层界面，或无法合理嵌入任何地方的流程）。

按项目已有的路由约定创建一个**一次性路由**。不要发明新的顶层结构。命名时要让它明显是原型（例如在路径或文件名中包含 `prototype` 一词）。使用同样的 `?variant=` 模式。

在决定采用子形式 B 之前，做一次合理性检查：是否真的没有任何现有页面可以嵌入它？一个空路由会掩盖设计问题，而一个已有内容的页面则会把这些问题暴露出来。

两种子形式中，浮动底部栏完全相同。

## 流程

### 1. 陈述问题，并选定 N

默认使用 **3 个变体**。超过 5 个，它们就不再是截然不同的，而变成噪音，因此以 5 个为上限。

用一行话写下计划，放在原型所在位置或文件顶部的注释中：

> "现有 `/settings` 路由上的设置页三个变体，通过 `?variant=` 切换。"

无论用户是否在场、是否会提出反对意见，这样写都行得通。

### 2. 生成截然不同的变体

起草每个变体。每个变体都要满足：

- 页面的用途，以及它可以访问的数据。
- 项目的组件库/样式系统（TailwindCSS、shadcn、MUI、原生 CSS，任何在用的都行）。
- 清晰的导出组件名，例如 `VariantA`、`VariantB`、`VariantC`。

变体必须在**结构上**截然不同：布局不同、信息层级不同、主要交互入口不同，而不只是颜色不同。三个略微调整过的卡片网格不算 UI 原型，那只是墙纸。如果两份草稿过于相似，就带着明确的"不要使用卡片网格"指引重写其中一份。

### 3. 把它们连接起来

在路由上创建一个单一的切换组件：

```tsx
// 伪代码，请根据项目的框架调整
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

子形式 A（现有页面）：把所有现有的数据获取保留在切换器之上；每个变体只改变渲染的子树。

子形式 B（新页面）：`/prototype/<name>` 下的一次性路由挂载同一个切换器。

### 4. 构建浮动切换器

屏幕底部居中的一个小型固定定位栏，由三部分组成：

- **左箭头**：切换到上一个变体（循环）。
- **变体标签**：显示当前变体的键；如果该变体导出了名称，也一并显示。例如 `B (Sidebar layout)`。
- **右箭头**：切换到下一个变体（循环）。

行为：

- 点击箭头会更新 URL 查询参数（使用框架的路由，例如 Next 上的 `router.replace`、React Router 上的 `navigate` 等），使变体可以分享，并在刷新后保持不变。
- 键盘：`←` 和 `→` 方向键同样可以切换。当 `<input>`、`<textarea>` 或 `[contenteditable]` 获得焦点时，不要拦截方向键。
- 在视觉上与页面区分开（例如高对比度的药丸形状、细微阴影），使它显然不属于被评估的设计的一部分。
- 在生产构建中隐藏：以 `process.env.NODE_ENV !== 'production'` 或等效检查进行控制，使一次误合并的原型无法把这个栏发布给用户。

把切换器放在单一的共享组件中，使两种子形式都能复用。把它放在项目共享 UI 所在的任何位置。

### 5. 交付

给出 URL（以及 `?variant=` 的各个键）。用户会在方便时逐个翻看。最有价值的反馈通常是"我想要 B 的头部加上 C 的侧边栏"，那才是他们真正想要的设计。

### 6. 记录答案并清理

一旦某个变体胜出，就记录答案（哪个变体，以及原因），然后按 [SKILL](SKILL.md) 中的描述保存原型。把获胜者并入真正的代码，其余的转移到一次性分支上，而不是留在 main 中：

- **子形式 A**：把获胜者并入现有页面；从 main 中删除落选的变体和切换器。
- **子形式 B**：把获胜的变体提升为正式路由；从 main 中删除一次性路由和切换器。

完整的变体集合就是一手来源，因此应保存在一次性分支上，而不是丢弃，因为若把变体组件和切换器留在 main 中，它们会很快腐烂，并使下一位读者困惑。

## 反模式

- **只在颜色或文案上不同的变体。** 那是微调，不是原型。真正的变体在结构上彼此不同意。
- **变体之间共享过多代码。** 共享的 `<Header>` 没问题；共享的 `<Layout>` 会破坏初衷。每个变体都应当可以自由地抛弃布局。
- **把变体连接到真实的变更操作。** 只读原型没问题。如果某个变体需要修改数据，就让它指向一个桩：问题是"这应该长什么样"，而不是"后端能不能工作"。
- **把原型直接提升到生产环境。** 变体代码是在原型约束下编写的（没有测试，错误处理最少）。并入时应当正式重写。
