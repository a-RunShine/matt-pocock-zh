# 逻辑原型

一个单独的、自包含的 HTML 文件（一个**可分享的演示**），让任何人都能通过点击按钮来推动状态模型运行。当问题关乎**业务逻辑、状态转换或数据形态**时使用：这类东西在纸面上看起来合理，但只有把它推过真实案例后，才会感觉不对。

因为它只是一个无需安装任何东西的文件，你可以把它交给非开发人员（设计师、产品经理、领域专家），让他们亲自体会模型。它说的是他们的语言，而不是代码的语言。

## 何时适用这种形式

- "我不确定这个状态机能否处理 X 之后再 Y 的边缘情况。"
- "这个数据模型真的能表示……的情况吗？"
- "在写 API 之前，我想先感受一下它应该是什么样子。"
- 任何有人希望**按按钮、看状态变化**的场合。

如果问题是"这应该长什么样"，那就选错了分支。请改用 [UI.md](UI.md)。

## 流程

### 1. 陈述问题

在写代码之前，先写下你正在原型化的状态模型以及要回答的问题。一段话，放在演示的顶部（在一个可见的介绍中，而不只是注释里）。回答错误问题的逻辑原型纯属浪费，因此要把问题明确写出来，以便之后检验，无论用户是现在在看，还是离开后再回来。

### 2. 把逻辑隔离在一个可移植的模块中

把真正的逻辑（即回答问题的那部分）放在单个 `<script>` 块中，写成一个小型的纯模块，日后可以整体取出，放进真正的代码库。包裹它的页面是一次性的；这个模块不是。

正确的结构取决于问题：

- **纯 reducer**：`(state, action) => state`。当动作是离散事件、状态是单一值时很合适。
- **状态机**：显式的状态和转换。当"当前哪些动作是合法的"本身就是问题的一部分时很合适。
- **一组作用于普通数据类型的纯函数**。当不存在隐式的当前状态，只有变换时很合适。
- **一个具有清晰方法表面的类或模块**，当逻辑确实拥有持续变化的内部状态时。

选择最适合所提问题的结构，而*不是*最容易接到页面上的结构。保持它的纯粹性：不涉及 DOM，不涉及 `document`，不让按钮处理函数伸进其内部。页面调用它；数据不会反向流动。正是这一点使原型在其自身生命周期之后依然有用：问题得到回答之后，经过验证的 reducer / 状态机 / 函数集合可以独立地提取进真正的模块。

### 3. 构建可分享的 HTML 文件

一个文件，纯 HTML/CSS/JS：没有框架、没有打包工具、没有服务器，所有内容都内联，使它可以通过双击打开，并且可以通过邮件转发。任何人打开它都应该能运行。

为非开发人员来写。每个标签都使用**领域语言**，而不是代码：按钮和状态读起来像业务，而不是 reducer。用平实的语言解释正在发生什么。

按从上到下的清晰层级来布局：

1. **标题和一行说明**，说明本演示让你探索什么（即第 1 步中的问题）。
2. **当前状态**：完整的相关状态，渲染为一个可读的面板（带标签的字段，而不是原始的 JSON 转储），每次点击后重新渲染，使变化可见。在有助于非开发人员跟上的地方，指出刚刚发生了什么变化。
3. **自由操作按钮**：每个动作一个按钮，始终可用，使任何人都能以任意顺序戳一戳这个模型。每次点击都分发其动作并重新渲染状态。
4. **引导式演练**：一组**场景**，每个标签页一个。每个标签页包含一段简短的、平实语言的场景描述（它设定的情境以及需要留意什么），下面是该场景要按下的、有序的**按钮**。每一步都是一个真正的按钮：点击它会执行该动作并进入下一步。开始演练会重置到已知的初始状态，使该场景每次都以相同的方式运行。

选择能展示棘手情况的场景：那些在纸面上难以推理的情况。例如正常路径、一个棘手的边缘情况，或一次本应非法的尝试。

保持美观但克制：干净的排版、宽裕的间距、一种强调色。没有动画，没有花哨的效果：任何东西都不能与状态和按钮争夺注意力。

### 4. 交付

把文件发给他们，或者替他们打开。他们会在方便的时候点击演练和自由操作。最有意思的时刻是他们说"等等，这不可能发生"或"咦，我以为 X 会不一样"；那些就是*想法*中的漏洞，这正是全部意义所在。如果他们想要新的动作或新的场景，就把它们加上。原型是会演进的。

### 5. 记录答案和原型

一旦原型回答了它的问题，就记录答案，然后按 [SKILL](SKILL.md) 中的描述保存原型。针对逻辑的具体映射：经过验证的 reducer / 状态机 / 函数集合提取进真正的模块（决定被吸收）；HTML 外壳随一次性分支一起保存，该分支把原型作为一手来源保留；由于它是一个自包含的文件，在那里它仍然可以轻松地重新运行。

## 反模式

- **不要添加测试。** 需要测试的原型就不再是原型了。
- **不要连接到真实数据库。** 除非问题专门关于持久化，否则使用内存状态。
- **不要泛化。** 不要说"如果以后我们想支持 X 怎么办"。原型只回答一个问题。
- **不要把逻辑和页面混在一起。** 如果纯模块引用了 DOM、`document` 或按钮处理函数，它就无法被整体提取。把页面保持为纯模块之上的一个薄外壳。
- **不要引入框架、打包工具或服务器。** 收件人双击的一个文件；一个 React 应用或开发服务器会破坏"可分享"。
- **不要把 HTML 外壳发布到生产环境。** 页面是为人工点击而优化的。它背后的逻辑模块才值得保留。
