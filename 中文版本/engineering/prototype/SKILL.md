# 原型（Prototype）

原型是**用来回答问题的一次性代码**。问题决定了它的形态。

## 选择分支

根据用户的提示、周围的代码，或在用户在场时直接询问，确定正在回答的是哪个问题：

- **"这个逻辑/状态模型感觉对不对？"** → [LOGIC.md](LOGIC.md)。构建一个可分享的单个 HTML 文件（包含自由试玩按钮和分标签页的引导式演练），将状态机推进到那些难以在纸面上推理的情况，并且非开发人员也能操作。
- **"这应该长什么样？"** → [UI.md](UI.md)。在单个路由上生成几种截然不同的 UI 变体，通过 URL 查询参数和浮动底部栏进行切换。

这两个分支产出的东西非常不同，选错会浪费整个原型。如果问题确实含糊，而用户又无法联系到，就默认选择与周围代码更匹配的分支（后端模块 → 逻辑；页面或组件 → UI），并在原型顶部说明该假设。

## 适用于两者的规则

1. **从第一天起就是一次性的，并明确标记为一次性。** 将原型代码放在其实际使用位置附近（紧挨着它所原型化的模块或页面），使上下文一目了然；但命名要让粗心的读者一眼看出这是原型，而不是生产代码。对于一次性的 UI 路由，遵循项目已有的路由约定；不要发明新的顶层结构。
2. **运行起来非常简单。** UI 原型应能通过任务运行器中的一条命令启动：`pnpm <name>`、`python <path>`、`bun <path>` 等。逻辑演示则是一个用户双击即可打开的单个 HTML 文件。无论哪种方式，启动都不需要任何思考。
3. **默认不做持久化。** 状态保存在内存中。持久化是原型_所要检验的_东西，而不应是它所依赖的东西。如果问题明确涉及数据库，就使用一个测试数据库或一个本地文件，并给它一个清晰的名称，例如 "PROTOTYPE, wipe me"（原型，可清空）。
4. **省去打磨。** 不需要测试、不需要超出"使其可运行"所需的错误处理，也不需要抽象。目的在于快速学到东西。
5. **展示状态。** 每次操作之后（逻辑类），或每次切换变体之后（UI 类），都要打印或渲染完整的相关状态，让用户能看清发生了什么变化。
6. **完成后将其保存下来。** 将任何已验证的决定折叠进真正的代码中，然后将原型本身作为**一手来源**保存下来：把它提交到一个一次性分支上，与主分支分开，并在实现 issue 上留下指向该分支的上下文指针。把结论（判定结果，以及它所解决的问题）记录在 issue 或某次提交中。主分支只保留已验证的决定。
