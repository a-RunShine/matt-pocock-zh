# ADR 格式

ADR 存放在 `docs/adr/` 中，使用顺序编号：`0001-slug.md`、`0002-slug.md`，依此类推。

只有在需要第一份 ADR 时，才惰性地创建 `docs/adr/` 目录。

## 模板

```md
# {决定的简短标题}

{1–3 句话：背景是什么，我们决定了什么，以及为什么。}
```

就这些。一份 ADR 可以只是一段话。它的价值在于记录_某个决定已经做出_以及_其原因_，而不在于填满各个小节。

## 可选小节

只有当它们确有实质价值时才加入。大多数 ADR 用不着它们。

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：当决定被重新审视时有用
- **Considered Options（考虑过的方案）**：只有当被否决的替代方案值得记住时才加入
- **Consequences（后果）**：只有当不显而易见的下游影响需要说明时才加入

## 编号

扫描 `docs/adr/`，找出当前最大的编号，然后加一。

## 何时提议 ADR

以下三条必须同时成立：

1. **难以逆转**：日后改变主意的代价相当可观
2. **脱离语境就令人惊讶**：未来的读者看到代码时会想"他们究竟为什么要这样做？"
3. **真实权衡的结果**：存在真正的替代方案，而你基于具体理由选择了其中一个

如果一个决定很容易逆转，就跳过它：你很快就会把它逆转掉。如果它并不令人惊讶，就没有人会疑惑为什么。如果当初没有真正的替代方案，那么除了"我们做了显而易见的事"之外，就没有什么值得记录的。

### 什么符合条件

- **架构形态。**"我们使用单体仓库。""写模型是事件溯源的，读模型投影到 Postgres 中。"
- **上下文之间的集成模式。**"Ordering 与 Billing 通过领域事件通信，而不是同步 HTTP。"
- **带有锁定效应的技术选择。**数据库、消息总线、认证提供方、部署目标。不是每个库，只是那些换掉需要一个季度的东西。
- **边界与范围决定。**"客户数据归 Customer 上下文所有；其他上下文只通过 ID 引用它。"明确的"不做"与明确的"做"同样有价值。
- **刻意偏离显而易见的路径。**"我们使用手写 SQL 而不是 ORM，原因是 X。"任何一个理性的读者都会假设相反结论的地方。这些记录能阻止下一位工程师"修复"一个本是刻意为之的东西。
- **代码中看不见的约束。**"由于合规要求，我们不能使用 AWS。""由于合作伙伴 API 的契约，响应时间必须低于 200ms。"
- **非显而易见的被拒替代方案。**如果你考虑过 GraphQL，但因为一些微妙的原因选择了 REST，就把它记下来；否则六个月后会有人再次建议 GraphQL。
