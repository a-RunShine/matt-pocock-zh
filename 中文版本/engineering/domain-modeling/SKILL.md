# 领域建模

在设计过程中主动构建并打磨项目的领域模型。这是一种*主动*的纪律：质疑术语、构造边缘情况的场景，并在决定明确成形的那一刻，把术语表和决定写下来。（仅仅*阅读* `GLOSSARY.md` 以获取词汇，不属于本 skill：那只是任何 skill 都可以养成的一个小习惯。本 skill 是在你要*修改*模型、而不仅仅是*使用*它的时候使用的。）

## 文件结构

大多数仓库只有一个上下文：

```
/
├── GLOSSARY.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

如果根目录下存在 `GLOSSARY-MAP.md`，则说明仓库有多个上下文。该地图指向每个上下文所在的位置：

```
/
├── GLOSSARY-MAP.md
├── docs/
│   └── adr/                          ← 系统级决定
├── src/
│   ├── ordering/
│   │   ├── GLOSSARY.md
│   │   └── docs/adr/                 ← 上下文相关的决定
│   └── billing/
│       ├── GLOSSARY.md
│       └── docs/adr/
```

按需创建文件：只有在确实有内容要写时才创建。如果不存在 `GLOSSARY.md`，就在解决第一个术语时创建它。如果不存在 `docs/adr/`，就在需要第一份 ADR 时创建它。

## 会话期间

### 对照术语表进行检验

当用户使用的某个术语与 `GLOSSARY.md` 中已有的语言相冲突时，立即指出来。"你的术语表把'cancellation'定义为 X，但你似乎指的是 Y。到底是哪一个？"

### 锐化模糊的语言

当用户使用含糊或被过度使用的术语时，提出一个精确的规范术语。"你说的'account'：是指 Customer 还是 User？这两者是不同的东西。"

### 讨论具体场景

当讨论领域关系时，用具体的场景来检验它们。构造能够探测边缘情况的场景，迫使用户把概念之间的边界说得精确。

### 与代码交叉核对

当用户陈述某件事是如何运作的时，检查代码是否与之一致。如果发现矛盾，就把它指出来："你的代码会取消整个 Order，但你刚才说可以部分取消。哪个才是对的？"

### 就地更新 GLOSSARY.md

当一个术语被确定下来时，立即在 `GLOSSARY.md` 中更新它。不要把它们攒着一起处理：一出现就记录。格式参见 [GLOSSARY-FORMAT.md](./GLOSSARY-FORMAT.md)。

`GLOSSARY.md` 应当完全不含实现细节。不要把 `GLOSSARY.md` 当作规格说明、草稿本或实现决定的存放处。它就是一份术语表，仅此而已。

### 谨慎地提议 ADR

只有当以下三条全部成立时，才提议创建 ADR：

1. **难以逆转**：日后改变主意的代价相当可观
2. **脱离语境就令人惊讶**：未来的读者会想"他们为什么要这样做？"
3. **真实权衡的结果**：存在真正的替代方案，而你基于具体理由选择了其中一个

只要缺少其中任何一条，就跳过 ADR。格式参见 [ADR-FORMAT.md](./ADR-FORMAT.md)。
