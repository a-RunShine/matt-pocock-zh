**软件工厂**是一套智能体系统，它把工单、PR 和定时任务变成已合并的代码，部署在用户选定的远程基础设施上。本 skill 是设计这种工厂的语言。在讨论或白板推演工厂时，只使用这里的术语；当用户用到 _Avoid_ 下的词时，指出规范术语。

## 任务与运行

**Task（任务）**：
工厂执行的一类工作，只定义一次，可运行多次：评审、探索、实现、棘轮。一个任务可以针对某张工单、某个 PR，或整个代码库来工作。
_Avoid_: job, workflow, action

**Trigger（触发器）**：
启动一次运行的事件：工单跟踪器或 git 托管平台上的变更、编排器中的时钟，或另一次运行。

**Run（运行）**：
一个任务在一个执行器上的一次执行，从触发到结束，视为黑盒。一次运行可以直接、通过编排器中的逻辑，或通过修改工单跟踪器或 git 托管平台，触发更多运行。运行从不等待人类：它结束，而人类之后对工单跟踪器或 git 托管平台的修改会触发新的运行。
_Avoid_: session

**Runner（执行器）**：
一次运行所在的一次性机器。即使机器本身是长期存在的，其上的东西也不会在运行之后留存：一次运行对早先运行的唯一记忆，是工单跟踪器、git 托管平台和编排器。
_Avoid_: server, host, box, compute, sandbox

## 服务

**Ticket tracker（工单跟踪器）**：
工单所在之处，也是工厂的人机界面：人类通过提交工单来安排工作，在评论中与智能体交谈，而他们对工单的修改会触发运行。
_Avoid_: issue tracker, ticket manager, project board

**Ticket source（工单来源）**：
工厂之外、在工单跟踪器中创建工单的任何东西：反馈按钮、监控、错误追踪器、收件箱。
_Avoid_: data source, trigger source, intake

**Git host（git 托管平台）**：
分支、PR 和评审所在之处。
_Avoid_: code host, forge, repo

**Orchestrator（编排器）**：
接收触发器、在执行器上启动运行，并记录哪些运行在排队、进行中或已结束的组件。
_Avoid_: dispatcher, scheduler, control plane

**Observability platform（可观测性平台）**：
执行器把日志、追踪和状态发送到的地方，让人类能看到每次运行内部发生了什么。这是可选的：占据执行器或编排器位置的产品往往自身就能提供足够的信息。在某件东西把它写入工单跟踪器或 git 托管平台之前，运行从不依赖它做决定。
_Avoid_: observability, logs, monitoring, dashboard

## 设计工厂

一个设计分为两半：**服务**（每个都是一个由产品填充的槽位），以及由运行推动工作穿过这些服务的**任务**。

从用户的问题出发，而不是从工厂出发：未经分诊的工单、等待自动评审的 PR、需要迁移到的更严格的自动检查、没人阅读的 bug。当用户提出某个问题或不知道要构建什么时，阅读 [EXAMPLE-TASKS.md](EXAMPLE-TASKS.md)，了解解决常见问题的任务。

### 先慢慢来

每个触发器都是加速器。没有刹车的加速器会制造一门「糊弄大炮」。有三种刹车：

- **自动检查**：每次运行都必须通过的确定性关卡（类型、lint、测试）。
- **自动评审**：一次独立的运行，在有工单时，依据代码库的标准和工单，冷读 diff。
- **人工评审**：人类在 PR 合并前阅读它；它抓到的问题会变成新的自动检查和更锋利的自动评审。

每次只加一个自动触发器，起初限流（十个 bug 报告中放行一个，时钟每天一次），并且每个 PR 都要人工评审。随着刹车赢得信任，逐步放开限流；每一个运行循环都要在交由人类之前限定在几次尝试之内。

### 填满每个槽位

每项服务都是一个槽位。一个产品可以填充多个槽位，一台服务器也可以承载多项服务。三种设计，并排对照：

| 服务                   | 全部用 GitHub                   | Linear 工单                    | 自建跟踪器               |
| ---------------------- | ------------------------------- | ------------------------------ | ------------------------ |
| 工单跟踪器             | GitHub Issues                   | Linear                         | 自建应用                 |
| 工单来源               | 反馈按钮                        | 反馈按钮、监控                 | 反馈按钮、监控           |
| git 托管平台           | GitHub                          | GitHub                         | GitHub                   |
| 编排器                 | GitHub Actions                  | 自建服务器 + 数据库            | 自建应用                 |
| 执行器                 | Actions 执行器                  | Actions、E2B、Daytona 或 VPS   | 自建应用，或沙箱         |
| 可观测性平台           | 无：Actions 运行页面已足够      | 某个 LLM 追踪平台              | 自建应用                 |

当用户为某个槽位挑选产品时，先读该槽位的调查文档以了解情况，然后自己研究当前的选项；每份调查文档都按类型对选项分组，并列出决定该槽位的问题：

- [TICKET-TRACKERS.md](TICKET-TRACKERS.md)
- [GIT-HOSTS.md](GIT-HOSTS.md)
- [RUNNERS.md](RUNNERS.md)
- [OBSERVABILITY-PLATFORMS.md](OBSERVABILITY-PLATFORMS.md)

购买服务，构建任务：任务承载用户的设计，服务则是通用的。优先选用现成的工单跟踪器：它稳健，人们已经熟悉，而且容易让外部用户接入。

### 逐个拷问任务

对每个任务，回答：

1. 什么触发它？
2. 它做什么，读写哪些服务？
3. 它接下来触发什么？
4. 人类在哪里重新介入？
5. 什么阻止两次运行做同样的工作？

对每个工单来源，回答：什么阻止它两次提交同一张工单？

当每个槽位都指明了一个产品（对可观测性平台而言，也可以是刻意的"无"），并且每个任务和工单来源对每个问题都有了回答时，设计才算完成。
