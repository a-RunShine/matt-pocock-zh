# 工单跟踪器

> 调查于 2026-10，不保证是最新的。用它来了解情况，然后自己研究当前的选项：产品、价格、限制和测试版都变化很快。

工单跟踪器是工厂的人机界面。下面每一类都是一个起点：先读它是什么、工厂什么时候会选它，然后对照 [进一步研究](#进一步研究) 中的问题检查各个例子。

## 类型

### 1. Git 托管平台内置的跟踪器

内置于 git 托管平台的跟踪器，因此工单、分支和 PR 共用一个产品、一套权限模型和一个身份。当工厂规模较小、团队已经在使用该 git 托管平台，或仓库是公开的时，工厂会选它。这是"全部用 GitHub"的设计：git 托管平台的 CI 无需胶水代码即可填充编排器槽位。标签是可靠的路由手段，因为状态位于另一个看板上。外部开发者在代码所在之处提交工单；非开发者需要一个账号，因此反馈按钮通过 API 提交工单。自托管的 git 托管平台会连同它的跟踪器一起部署。

- [GitHub Issues](https://docs.github.com/en/copilot/concepts/agents/about-third-party-agents)：默认选项；可将工单分配给 Copilot、Claude 和 Codex 等智能体。
- [GitLab Issues](https://about.gitlab.com/blog/how-to-use-a-work-item-created-trigger/)：由工作项触发的 Duo Agent Platform 流程。
- [Forgejo](https://forgejo.org/2026-10-release-v17-0/)：自托管，兼容 Actions。

待核实：哪些"分配给智能体"的功能仍处于预览阶段，以及哪些套餐包含它们；原生智能体是在分配时读取工单，还是也读取之后的评论（截至 2026-10，Copilot 只在分配时读取）。

### 2. 原生智能体的开发跟踪器

一款独立的 SaaS 跟踪器，面向软件团队，把智能体视为一等的被分配者，提供智能体 API 及其自带的编码智能体。当产品、客服或设计人员安排工作、团队本来就在那里工作，或希望得到精致的分诊和规划视图时，工厂会选它。这是"Linear 工单"的设计。状态和工作流是一等公民，因此"已移至就绪"是一个干净的触发器。智能体以应用用户的身份出现，由人类委派任务，运行过程可以把进度流式输出到工单中。这里的原生智能体在各类中集成最深，因此其中一个也可以部分地填充编排器和执行器槽位。

- [Linear](https://linear.app/developers/agents)：最像智能体形态的跟踪器。
- [Jira](https://support.atlassian.com/jira-software-cloud/docs/collaborate-on-work-items-with-ai-agents/)：由状态触发的智能体；适合已在使用 Atlassian 的组织。
- [Shortcut](https://www.shortcut.com/help/integrations/using-ai-agents)：分配一个故事，或在评论中提及智能体。
- [YouTrack](https://www.jetbrains.com/youtrack/)：工作流即代码；可自托管。

待核实：智能体 API 的状态（截至 2026-10，Linear 的仍处于开发者预览）；原生智能体运行如何计量和计费；智能体席位的成本；智能体 webhook 的确认期限；哪个套餐解锁面向客户的表单；自托管版本的停止支持日期。

### 3. 开源开发跟踪器

一款类似 Linear 的跟踪器，可以在你自己的基础设施上运行，旁边还有云版本。当数据必须留在内部（物理隔离、受监管），或用户希望在购买的同时还能阅读并修改跟踪器的源代码时，工厂会选它。按状态、标签和自定义属性路由的方式与第 2 类大体相同；原生智能体则较为年轻。

- [Plane](https://developers.plane.so/dev-tools/agents/overview)：类似 Linear；每个应用一个机器人用户；智能体在评论中回复。
- [Huly](https://github.com/hcengineering/huly-selfhost)：一体化工作区，支持与 GitHub 双向同步；运维栈较重。
- [OpenProject](https://www.openproject.org/)：成熟的经典项目管理工具。

待核实：智能体功能的状态（截至 2026-10，Plane 的仍处于测试版）；哪个版本包含访客角色和接收表单；许可证；自托管栈的运营成本。

### 4. 通用工作工具

一种工作管理或文档工具，其数据库或任务列表兼作跟踪器。当它服务于已在使用它的非工程团队，或工单主要是内容、运维或研究而非代码时，工厂会选它。表单是它的强项：任何拿到链接的人都能提交工单。路由依靠灵活的数据库属性，因此每个工厂都得自己设计一套模式。开发者上下文（diff、PR）在 git 托管平台上只需点一下即可查看。仅限 SaaS。

- [Notion](https://www.notion.com/help/custom-agents)：把数据库当作跟踪器；数据库变更时触发智能体。
- [Asana](https://asana.com/product/ai/ai-teammates)：AI 队友接手被分配的任务。
- [ClickUp](https://clickup.com/brain/cloud-agents)：云端智能体在任务线程中返回一个 PR。
- [Trello](https://developer.atlassian.com/cloud/trello/guides/rest-api/webhooks/)：看板和列表；webhook 加上 Butler 自动化。

待核实：webhook 的延迟和粒度（截至 2026-10，Notion 会批量处理内容更新，到达时晚一两分钟）；哪个套餐包含智能体。

### 5. 仓库原生跟踪器

工单以文件形式存放在仓库中（JSONL、Markdown），由智能体通过 CLI 或 MCP 服务器编辑，并像代码一样合并。当某位开发者在本地驱动智能体、希望计划留在 git 中，或把它作为一次运行的工作记忆放在真实跟踪器旁边时，工厂会选它。推送到 git 托管平台是唯一的触发器，因此编排器需要对比文件以找出变化。身份由 git 托管平台提供。外部提交工单只能通过 commit 或 PR，这在各类中最弱，因此一旦其他人也开始提交工单，工厂就应升级为 git 托管平台的跟踪器。

- [Beads](https://github.com/steveyegge/beads)：带依赖追踪的 JSONL，运行因此可以挑选下一张未被阻塞的工单。
- [Backlog.md](https://github.com/MrLesk/Backlog.md)：带看板视图和 MCP 服务器的 Markdown 任务。

### 6. 自建

工厂自己的应用把工单存放在自己的数据库中，通常与编排器放在一起。这是"自建跟踪器"的设计。当跟踪器本身就是产品（内部平台、面向客户的支持工厂），或没有任何现成方案适合时，工厂会选它。触发器变成函数调用；下面问题中的每一项特性都会变成需要编写和维护的代码，这正是本 skill 倾向于购买的原因。带有 webhook 的 [Airtable](https://airtable.com/developers/web/api/webhooks-overview) 数据表是一种半成品的中间方案。

## 进一步研究

对每个候选项，用以下问题逐一核对。它们决定了槽位的归属：

- **触发器**：哪些工单变更（创建、加标签、状态变更、分配、评论、被提及）会发出编排器能转化为运行的 webhook 或事件？速度如何，粒度多细？
- **路由**：运行可以读取哪些标签、状态或字段，以得知自己的类型（探索、实现、返工）？
- **线程**：人类能否在评论中回复智能体，这次回复会不会触发下一次运行？
- **身份**：是否有 API 加机器人身份，使运行以自己的身份行事，并让人类能分辨智能体与同事？机器人是否占用一个席位？
- **原生智能体**：工单能否直接分配给智能体？哪些智能体，在哪个套餐下，如何计量？它读取的是分配时的工单，还是整个线程？
- **外部提交**：工单来源或客户如何创建工单：表单、邮件、聊天，还是 API？哪个套餐解锁它？
- **托管方式**：仅 SaaS，还是可自托管？采用哪种许可证？

答案应来自一手来源：API 与 webhook 参考文档（事件列表、载荷、投递与重试规则）、智能体或应用的开发者文档、定价页面与套餐对比表，以及更新日志或发布说明。优先采用这些来源，而不是博客文章和对比网站。

按陈旧程度排序，最先核对：智能体功能及其预览或测试版状态、智能体的计量与信用价格、智能体与表单的套餐限制、速率限制，以及收购、关停和自托管版本的停止支持日期。webhook 事件列表和路由模型变化较慢。

## 持久的陷阱

在依赖之前，先核实每一条是否仍然成立：

- **GitHub 的 `GITHUB_TOKEN` 陷阱**：使用默认 `GITHUB_TOKEN` 所做的变更不会触发新的工作流运行。一个通过给工单加标签或评论来触发下一次运行的运行，应通过 GitHub App 令牌行事。
- **分配时的上下文**：有些原生智能体只在被分配时读取工单，因此之后补充的上下文应放在 PR 上。
- **智能体 webhook 要求快速确认**：编排器立即确认，之后再启动运行。
- **通用工作工具中的批量 webhook** 到达较晚；需要及时运行的工厂应基于属性变化触发，或改选其他类型。
